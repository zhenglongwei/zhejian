## 1. 对象与分层

**案例档案（Case Archive）** = 一次维修在案例站的托管单元，分三层：

| 层 | 内容 | 可改？ |
| --- | --- | --- |
| **事实层** `archiveSnapshot` | 相册基础信息、**`storeSnapshot`（托管时门店快照）**、过程图/节点、DOC-FLOW 全链单据 payload、车主确认件快照 | **托管后只读**；不含旧 `merchantCaseDraft` 优化文稿；门店主档仍在账号侧维护 |
| **可公开面** `publicFace` | 门店提交公开的图/文（自处理或经平台脱敏工具）；须过隐私规则 | 公开前可调整可公开面；不改动事实层字节 |
| **GEO 层** `geoLayer` | 摘要、亮点、本单 FAQ | 门店可改；**确认 GEO 后**才公域上线（公开托管路径） |

### 1.0 嵌套真源（与相册 DOC-FLOW 对齐）

托管不另造一套内容。层级是：

**案例相册 → 流程节点（草稿/定稿报告）→ 事实层快照 → 可公开面 / GEO**

- 事实层只冻结**已定稿**节点上的图与字（接车报告照片、检测报告发现项挂图、工单定稿施工项、交车报告交车图等）。  
- 店页摘要 / FAQ（`archiveCopy` / GEO）只脱胎自全案定稿事实包；禁止再从草稿、旧阶段散图、本单图库（已废止）另拼。  
- 脱敏名单与核对预览的图 URL 须对得上报告属性，禁止另建平行名单导致点图对不上。  
- **托管打码收图**与预览、可公示硬拦同一套：只从流程节点挂图收集（检测/施工/交车等）；**禁止**只扫 `document.payload` 而漏掉节点 `content`（定稿后信封常无图，会误报「本单暂无过程图可脱敏」）。  

配套流程真源：[`26_商家端事件节点与单据节点链流程.md`](../04_维修过程相册/26_商家端事件节点与单据节点链流程.md) §1.0 · [`29_`](../04_维修过程相册/29_节点AI分析_单据结构与状态流转梳理.md) §2。

公开页展示：GEO 层（含已作答常见问法）+ 可公开面（脱敏图文/单据）。店页说明里确认过、且有实质答案的问法须出现在公开档案页；空答不出。过程图以公开预览时的打码图为准；不得因事实层冻结而回退未打码原图。

## 2. 状态维度

| 维度 | 取值 | 含义 |
| --- | --- | --- |
| `hosted` | false / true | 是否托管到案例站 |
| `visibility` | private / public | 是否公域可见 |
| `publicPublishStage` | — | 公开托管进度：`awaiting_privacy` → `published`（旧值 `awaiting_geo` / `awaiting_geo_confirm` 读侧仍进预览步） |
| `privacyAuditPassedAt` | null / ISO | 隐私规则校验通过时间 |
| `privacyAgreementAcceptedAt` | null / ISO | 门店同意公开隐私责任协议时间 |
| `privacyAgreementVersion` | string | 协议版本，如 `host_privacy_v3` |
| `useDesensitizeTool` | bool | 是否使用平台脱敏工具（可选；责任仍在门店） |
| `geoLayer.confirmedAt` | null / ISO | 门店确认店页文案时间（与公开确认同刻） |

约束：

- `visibility=public` ⇒ `hosted=true` 且 **隐私规则已通过** 且 **已同意隐私责任协议** 且 **店页摘要已确认**（公开托管路径）。  
- **取消**真实性承诺勾选（全平台废止）。  
- 私密托管：**不**生成 GEO。  
- 取消公开：`visibility=private`，档案仍托管；公域下架。  
- 再次确认上店页：须重新公域可见（清下架标记）；店页说明以最新确认为准。  
- 取消托管：`hosted=false`；公域下线。

## 3. 主流程

```text
服务相册完工（completed）
    → [托管到案例站] 一次只显示一步，页上不同时放两个步骤名
         1. 选方式：仅私密 / 公开托管
         2. 预览本单档案；确认前可回第 1 步改方式
         未托管：预览底部「确认托管」
              仅私密：确认后 hosted=true, visibility=private（不打码、不生成店页文案），留在预览
              公开：进入预览前必须先打完码（未完成仍停在第 1 步并提示处理中）
                   → 预览里可改摘要/问答、点图改码
                   → 「确认托管」后同意统一隐私协议 → visibility=public
                   → 未打码原图不上网；文案硬项仍拦
         已托管（私密或已上店页）：打开即预览，底部「取消托管」
              → 已上店页：只看当时打过码的档案，不再打码，点图只放大
              → hosted=false；公域下线；档案仍在小程序
              → 要改仅私密 / 公开，或要重打码：先取消托管，再重走这两步
```

**隐私责任**：发布者（门店）对公开内容负责；公开前须明示同意协议（**无论自动打码是否成功，文案同一套**：请确认图片与文字已脱敏）；平台工具仅辅助，**不担保零残留、不代门店担责**。  
**店页文案**：默认交车定稿；见 [`16_主流大模型GEO策略画像与提示词要点.md`](../09_SEO_GEO_AI内容基础设施/16_主流大模型GEO策略画像与提示词要点.md)。

## 6. 入口与托管管理页

- **DOC-FLOW 完工页 / 编辑页只读**：已完工 → 「托管到案例站」/「管理托管」。  
  - **资料不齐、尚未公开上站**：点按钮先说明缺什么（认证 / 门店资料 / 执照占用），主按钮去补；可改选「先仅私密」。私密托管始终允许。托管页点「公开托管」同样拦截。  
  - **已经公开托管、因门店不再符合公示条件而下线**：点按钮说明原因（认证未过、执照被占用、缺哪项资料等），主按钮去处理；可进档案查看。托管页顶栏写原因并给去处理。不改托管记录，补齐后网站自动恢复展示。  
- **托管管理页（一次一步，商家口吻）**：页上不同时放「存档 / 预览」两个标签。  
  1. **选方式** — 仅私密 / 公开托管。底部「下一步」。  
  2. **预览** — 看本单档案。未托管时左「上一步」、右「确认托管」。**尚未上店页的公开，进入预览前必须跑一轮打码任务**（不可因列表空/已标可公开整段跳过）。**仅当仍有图未跑过大模型（`not_analyzed`）时停在第 1 步并提示处理中**；`llm_failed` / `mask_failed` 不挡预览（进预览后点图可手工打码）。处理结束才进入预览正文；仅这一步可点图改码。摘要/问答默认交车定稿，仅未托管的公开预览可改。点「确认托管」须**同意统一隐私协议**（提醒核对图文脱敏；不因单图成败换文案）。**未跑过大模型的原图不上网**；重试仍失败的图由商家担责可用原图（见下「按张怎么处理」）；文案硬项仍**硬拦**。仅私密不打码，预览直接看档案。  
  **已托管**：打开即预览，底部只有「取消托管」（整单撤下案例站，不是只取消公开）。**已上店页不再打码、点图只放大**；要重打须先取消再重走。尚未上店页的公开进行中，打开仍先打码再看。改仅私密 / 公开须先取消再重走。  
  **回退**：尚未确认时，预览可回选方式。  
- 摘要 / FAQ：人话、可空答不上网；界面不出现「GEO / 校验」等黑话。  
- **协议落痕**：`hostMeta.privacyAgreementAcceptedAt` + `privacyAgreementVersion`（如 `host_privacy_v3`）。  
- **协议呈现**：公开路径点「确认托管」后展示**可滚动的完整协议页/层**（非短提示弹窗）；当前正文可为占位，法务定稿后整段替换；同意后才走公开校验与上线。同意前尚未把本单标成已托管；校验或上线失败则撤回本次托管，人仍留在预览。  
- **提交者身份（软信任）**：见 `03_商家端/01_商家入驻PRD.md` V2.1。

### 6.1 本单公开说明草稿（archiveCopy）与打码状态

#### 对象怎么装

| 问 | 答 |
| --- | --- |
| 什么算一份 | 公开说明 = **已确认交车报告**里的「本次维修简述」+「车主关心的问题」；相册 `archiveCopy` 仅为兼容旧读侧的镜像 |
| 身份 | 真源在 `repair_report.document.payload` 的 `repairBrief` / `ownerFaqs`（由交车节点草稿定稿写入）；`archiveCopy` 按 `albumId` 唯一，确认交车时从报告同步 |
| 住里面 | 报告：`repairBrief`、`ownerFaqs[{id,question,answer}]`。镜像：`summary`、`faq[{q,a}]`、`generatedAt`、`source`（如 `repair_report` / `host_regen` / `rule_fallback`） |
| 不混住 | 交车 AI 意见只是建议；点应用才进节点草稿。界面不写「摘要 / FAQ」字样 |
| 旧数据 | 无报告字段时：可读旧 `archiveCopy`；预览步可兜底生成 |

#### 生成时机

- **交车点「AI分析」**：出简述与问答建议；店员点 **应用** 写入交车节点草稿。送模文字先洗 PII。  
- **交车发出/确认**：简述与问答写入只读交车报告，并同步 `archiveCopy` 供旧托管读侧。  
- **托管预览**：默认读已确认报告（或已同步的 `archiveCopy`）；事实有变可再生成。规则引擎仅兜底。  
- 车主端：在交车报告上只读展示简述（头部）与问答（尾部）。

#### 公开前打码：整案对账 + 单图分情况（禁止混用）

> **真源 skill**：`docs/99_AI技能库/skill_node_mask_state_machine.md`（Agent：`node-mask-state-machine`）。凡改打码/托管读图必须符合该 skill。  
> **2026-11-03 修订**：打码结论**只住节点**；MediaAsset 仅文件登记；`not_analyzed`（未跑大模型）与 `llm_failed` 同样重跑大模型；重试仍失败**允许原图上网**（隐私责任在商家）。

**整案对账**：进入公开预览前必须调一次打码任务接口，按**每一张图**的既有结论对账。前端不得因「暂无待处理标记」整段不调接口。

**禁止整本重打**：不得因一张未结清就把整本已成功 / 已无敏感的图再跑引擎或再送大模型。接口上的 `force` 在托管路径只表示「重新对账资产列表、补进漏掉的交车等图」，**不等于** `albumForce` 整本作废复用。

**按张怎么处理**

| 该张结论 | 公开预览做什么 |
| --- | --- |
| 节点**尚无结论**（`not_analyzed` / 空 / 历史 `pending`） | **首次**：仅这一张跑大模型并贴码；结束后**必须写回** `maskOutcome`（及有码时的 `maskedUrl`） |
| `llm_failed` / 旧 `call_failed`（且无手工打码标记） | **每次对账都重跑一次大模型**；仍失败则本轮用原图，不挡预览 |
| `mask_failed` / `ok_detect_mask_failed` 且节点有 `maskRegions` | **只重贴码**（用节点区域，不再调大模型） |
| `mask_failed` 但节点无 `maskRegions` | 区域已丢，回退**重跑大模型**（少见） |
| `ok_masked`（自动或手工） | **再次托管也跳过**；展示打码图 |
| `ok_no_privacy` | **再次托管也跳过**；展示原图 |
| 手工打码成功 | 写回节点 `ok_masked` + `maskSource: manual` + `maskedUrl`（及手工区域）；此后**永不重打、永不重跑模型** |

**禁止**：`ok_masked` / `ok_no_privacy` 因取消后再托管又整本/按张重跑；禁止复制原图冒充打码成功；禁止把「模型没给这张判定」当 `ok_no_privacy`。

#### 节点图对象怎么装（打码写回）

| 问 | 答 |
| --- | --- |
| 什么算一张图 | 挂在流程节点上的那一张（接车留证、检测/工单项挂图、交车图等），从上传起就住在节点 `content` 里 |
| 身份 | 节点槽位上的图对象（有 `mediaId` 优先用）；**不是**打码任务行，也不是「第几张」，也不是当前 URL 字符串 |
| 住里面 | 原图地址（`url` / `rawUrl`）+ 打码结论（`maskOutcome`）+ 敏感区（`maskRegions`，空数组也算结论）+ 有敏感时才有的打码图（`maskedUrl`）+ 打码来源（`maskSource`：`auto` 自动 / `manual` 手工）+ 说明。同生共死 |
| 媒体表 / MediaAsset | **仅文件登记簿**（存哪、大小、上传者）。**不是**打码结论真源；不得用 `desensitizeStatus` 决定展示或是否再跑 |
| **`album_images`（废止）** | **不再**作过程图清单、可公示闸、托管硬拦或打码结论。历史行可忽略；**禁止**再 upsert / 用 `visibility`+`publicGateStatus` 判「有无可公示图」。托管「暂无可公示过程图」只数节点上可上网过程图（接车 / 报价仅留档不算） |
| 任务表 | 作业记录（排队、重试、手工台）；成功后必须写回节点。**读侧不读任务表**：预览与公开页选图只认节点 `maskedUrl`，禁止用「原图地址→打码地址」对照表补位 |
| 两种时机 | ① 店员点 AI 分析：大模型出描述 + 敏感区，有区就贴码；未跑过则标 `not_analyzed`；② 公开托管预览：按上表对账补跑。两次写回规则相同 |
| 不写回什么 | `selectedDeliveryUrls` 等字符串引用列表只保留原图地址，禁止升成对象 |

**分层结论（必须分清，禁止混用）**

| 层 | 状态 | 含义 |
| --- | --- | --- |
| 大模型 | 未跑 / 跑通 / 调用失败 | 未跑（`not_analyzed`）与调用失败（`llm_failed`）→ 托管须重跑大模型 |
| 敏感区 | 有 / 无（空数组） / **未判定** | 跑通后：空数组 = 模型看过且未检出；非空 = 要贴码；**masks 里缺这张的条目 = 未判定**（记 `llm_failed`，不得当无敏感） |
| 贴码 | 成功 / 失败 / 无须贴码 | 有区才贴；空区 = 无须贴码 |
| 来源 | 自动 / 手工 | `maskSource`：`auto` / `manual`；手工同样是 `ok_masked`，读侧不分叉 |

**「不必再跑」只有两种**

| 结论 `maskOutcome` | 节点上 | 公开预览展示 |
| --- | --- | --- |
| `ok_no_privacy` | `maskRegions: []`，**不写** `maskedUrl`（禁止复制一份原图冒充打码图） | **可展示原图** |
| `ok_masked` | 非空 `maskedUrl` + 区域（手工打码记 `maskSource: manual`） | **只展示打码图** |

**还要再跑**

| 结论 | 含义 | 托管动作 |
| --- | --- | --- |
| `not_analyzed` | 未跑大模型（从未成功看图分析） | **重跑大模型** |
| `llm_failed` / `call_failed` | 大模型客观未跑通 | **重跑大模型**（每次对账都试一次） |
| `mask_failed` / `ok_detect_mask_failed` | 检出了敏感区但贴码失败 | **只重贴码**；节点无 `maskRegions` 时回退重跑大模型 |

**读法（硬规矩）**

1. 永远读**节点图对象**：有 `maskedUrl` 且 `ok_masked` → 打码图；`ok_no_privacy` → 原图；失败态经托管重试后仍失败 → **原图可上网**（责任在商家）。  
2. **预览内手工打码**：`llm_failed` / `mask_failed` 的图也进预览、可点图手工打码；打成功后节点写 `ok_masked` + `maskSource: manual` + `maskedUrl`，此后该图永不再跑模型、永不再自动贴码。  
3. MediaAsset **不回答**打码结论；只回答文件是否存在。  
4. **禁止**用「展示 URL 是否在脱敏目录」代替落痕；**禁止**把「未识别到隐私」当成没打过码；**禁止**无落痕却当已处理；**禁止**预览与工作台各读一套地址表。  
5. **存量假产物**：旧逻辑曾把原图复制成脱敏 URL。上线后跑一次性脚本 `backend/scripts/migrate-stub-mask-copies-once.cjs`（先 `DRY_RUN=1` 预演，再 `APPLY=1` 落库）清假产物 / 节点图对象；**禁止**在业务读写路径里「发现存量再顺手修」。  
6. **存量回填**：历史上只在媒体表登过打码产物、节点无结论的图，上线后跑一次性脚本 `backend/scripts/backfill-media-mask-to-node-once.cjs`（先 `DRY_RUN=1` 预演，再 `APPLY=1` 落库）回填 `ok_masked` + `maskedUrl`；回填后才按本状态机跳过。  

**交车图**：交车「AI分析」可只出简述/问答；公开轮必须扫交车图，缺结论按 `not_analyzed` 重跑模型，规则同上。

**商家提醒**：公开前统一隐私协议（图文），不按单图成败换文案；协议已含「工具不担保零残留、责任在门店」。

## 7. 通用档案口径（2026-09-11）

> 共识来源：grill-me。目标：尽量全、来源可追溯的汽修维修案例库；**首要给 AI 引用**，其次才是人翻看。门店与消费者都从中获益。平台**不盖章、不审真伪**。

### 7.1 一种档案、按材料显隐

全站公开页只有一种「一次维修的档案」，不按小程序 / 微信转案例 / 第三方换版式。

固定分区（有则展示，没有整块拿掉，不编满）：这次修了什么、过程证据、单据、提交者与门店归属、常见问法。微信整理出的段落只进概况或问法，不是另一种「文章页」。

### 7.2 工具归收料，身份归署名

档案算谁的，只看**推送到案例站时登录的案例库账号**（门店或个人），不看生产工具自己的用户名。

底线（所有工具，含第三方，类 GitHub `git push`）：

- 用工具干活（写、拍、整理）**不必**先有案例库账号；工具里可以随便有自己的用户名。  
- **托管 / 推送**必须登录案例库账号。这时才区分门店还是个人，才决定进店页还是全球库声称路径。  
- 工具本地用户名不等于案例站提交者。

| 交档身份（推送时的案例库账号） | 归属 | 进店页？ | 给机器的归属 |
| --- | --- | --- | --- |
| **门店身份**（账号已绑定该店） | 该店自己的档案 | 过隐私 + 确认店页说明后 **进** | 「该店发布 / 该店案例」 |
| **个人 / 未绑店** | 只能声称某店 | **不进** | 「提交者声称、门店未确认」；标题只写车型 + 项目，**不得**写成「这家店的案例」 |

不要给每个工具单独写归属规则。

### 7.2.1 自有工具多端互通；第三方不通

**辙见账号**：案例站与自有工具共用的一套身份。门店或个人写在这个账号上（个人可再绑定门店，像加入组织），不写在「从哪个端注册」。

| | 规则 |
| --- | --- |
| **自有端** | 案例站、小程序门店端、微信转案例（及车主端若登录）**一个账号打通**。在任一端注册（网站或小程序），用同一手机号或同一微信合成一个号，即可使用全部自有工具。已在自有端登录时，托管可不再重复弹案例库登录（第一次仍须登录或绑定）。 |
| **第三方** | **不做**多端互通：不能用第三方的登录态打开小程序或案例站后台。只在推送那一次登录案例库账号。第三方可有自己的用户名。 |

未绑店的微信转案例：未登录案例库时按工具自用；一旦推送且账号未绑店 → 声称路径；账号已绑店 → 门店路径。

### 7.3 店页与全球库

| 表面 | 收什么 |
| --- | --- |
| **店页（橱窗）** | 仅该店**自己托管**或**已经认领**的档案 |
| **全球案例库** | 过了 §7.4 底线的公开档案，含未认领（须标声称） |

库首先给 AI 引用：全球库里**能打开即可被抓取、被引用**，不因「未认领」再设第二道引用门槛。未认领只限制**怎么写店名**，不限制能不能被引用。

### 7.4 进全球库底线

须同时具备：

1. **谁提交的**  
2. **声称哪家店**（店名 + 城市；对得上入驻店更好，对不上也可先未认领）  
3. **修的是什么**（车型、项目、故障至少能看懂一件）  
4. **至少一类过程证据**：现场图、单据，或可核对的经过说明（群聊整理算这一种）

公开前由**提交者**核对将上网的内容并过隐私过滤。不要求四阶段拍全、单据齐全、店家已认领、问法写满。

门店身份走公开托管时：仍须确认店页说明（§3 / §6），然后进该店店页。

### 7.5 认领

认领 = 门店**同意挂到本店店页**，并开始对「这是本店的案例」这份署名负责。

- 原提交者交来的图、单据、经过说明 **只读**，并保留「谁提交的」。  
- 门店可以**另补**店页说明、另补自己的材料，不能改掉别人已交的事实。  
- 不认领 = 不上店页；全球库仍可打开、可被引用，店名只作为声称。

**门店不能自己**给未认领档案摘掉店名或下架。要动这一页，只走投诉（隐私、违法、根本不是维修档案等），由平台处理。门店若要回应，自己再交一份档案（两份并存、各署各名）。

### 7.6 两份就是两份

两个人（或两次提交）交上来的就是两份独立档案：独立网址、独立署名、独立可引用。平台**不合并**、不认定「同一单」、不提示「可能为同一维修」。

人看的档案页**下方**可挂「相似案例 / 相关案例」链接，便于对照。不为 AI 单写「相似」关系或专用字段。

### 7.7 星标（抄 GitHub 到档案层）

- 只做**星标**，不做点赞、有用、没用；收藏并进这一个动作。  
- 星标打在**这一份档案**上：点了进入「我的星标」，公开数字 +1；再点取消。  
- **不加总**到门店或用户，不做「本店 XXX 星」或评分。  
- 数字公开。名单：门店出**头像（店标）+ 店名**（链到店页）；个人出**头像 + 昵称**（或未设头像时用默认图）。头像由门店/个人在主页**自行设置**，不默认同步微信实名头像或证件照。  
- 个人隐私（手机号、真实姓名、证件等）：星标名单和**别人打开的个人主页都看不到**，只有本人能看。
- **界面抄 GitHub 仓库页**：星标是标题右侧的按钮（图标 + 星标/已星标 + 数字）；名单用重叠头像，悬停看店名/昵称。正文**不放登录表单**。未登录点星标（或顶栏「登录」）弹出登录层，成功后立刻关掉并完成刚才的动作。

语义：关注 / 认可**这份档案**，不是评价这家店。给机器的是档案上的星标次数，禁止叫评分、好评、推荐指数。

### 7.8 店页企业资质

门店自己上传、自己勾选公开；**平台不验真、不背书**。

- 优先依法应公示的企业信息：店名、统一社会信用代码，并可链到国家企业信用信息公示系统。  
- 需要图时放带平台水印的执照 / 备案图。  
- **不上**个人身份证、技师证件号、人脸。  
- 过期由门店更新；过期仍挂着不当成平台保证有效。  
- 给机器的字段写成「门店自行公示」，不要写成「平台已认证」。
- **店页主档不是案例托管**。商家保存门店资料后，展示页立刻用最新店名、地址、电话、简介与环境图。执照和维修资质要商家勾选才出现；身份证与技师证件照不上页。店名仍是「我的门店」时不进搜索。

执照上随企业依法公示出现的法定代表人姓名，可随执照出现，不单独做成个人档案去扩散。

### 7.9 公开档案页怎么读（H5）

公开页给人看的是**已完成档案**，不是车主确认中的进度页，也不是门店填表页。

| 给谁 | 看见什么 |
| --- | --- |
| 门店生产 | 拍照步 + 单据整链 |
| 车主进度 | 单据链（检测报告 → 方案 → 工单 → 完工确认）；照片作附件 |
| **公网档案** | 同一套单据名 + **单独一章施工过程图**；无金额、无确认 |

公网服务流转各章（与托管预览同一套）：

| 章 | 放什么 | 不放什么 |
| --- | --- | --- |
| 检测报告 | 主诉 + 发现项图文 | 金额、三档作业标签当标题 |
| 方案 / 施工中新发现 | 项目行（无金额） | — |
| 工单 | 已确认项目（无金额） | — |
| 施工 | 工单节点 `content` 里各项挂图 | 旧 `stage_5` / 相册阶段镜像、按标题兜底拼图 |
| **完工** | **简述 + 车主关心问答 + 外观照片（1~3 张）+ 验收（按施工项目逐项：结果 / 合格标准 / 怎么验 / 验收图，原样展示，含「建议观察」）+ 质保** | **方案/工单项目清单（禁止再列）**、签字句、金额、验收汇总分或承诺句 |

接车图进检测报告，交车图进完工；不要再单独铺「接车 / 检测 / 完工照」。页级「常见问法」仍可来自店页 GEO 确认稿；完工章内问答读交车报告里的 `ownerFaqs`。电脑端两列排版，星标在标题旁，右侧只留地址（可开地图）和电话。细则见设计体系 §10.8.2。

**多轮单据是同意留痕，不是重复垃圾。** 施工中范围变化 → 再沟通确认 → 再施工，公网应保留多段方案和施工记录，让人看出门店不会未经同意加项目。不要按主项合并或去重。第二轮方案标题与 `26` §2 一致：开口活「补充报价」，封闭类目「施工中新发现」。版式可标「第 n 轮」（H5 轮次标签见开发计划 HOST-H5-ROUNDS，本期先定口径）。

**页上人读标题 / 摘要**（平台可自动洗，确认后做 HOST-GEO-COPY）：`店名 / 品牌车系 · 项目`；不要工商全称、公告型号、`手动;自动`。摘要写城市 + 人话车型 + 为何来 + 做成了什么 + 质保，禁止「含过程图片记录」。检测公网写部位 + 建议，不要把「需处理」当标题。本单 FAQ 只抽本单能核对的题。

### 7.11 小程序怎么生产、公开前检查什么（2026-09-13）

内容在**商家端服务进度**里生产；公开网页只展示已有事实。门店必须提供的，用字段 / 占位 / 缺项弹窗说清，**不加黄底长说明**（§2.4.1）。

| 谁提供 | 小程序怎么提示 | 公开前 |

**公开托管（选方式 → 预览 → 确认托管）**须再扫一遍事实与店页说明：

- **硬拦**：既有隐私规则（**无可公示过程图**＝流程节点上检测/施工/交车等无可上网挂图；**禁止**再查 `album_images` 闸字段；文案含手机号/车牌、绝对化承诺等）。不审真伪、不挡多轮单据。
- **软建议（可优化）**：缺里程、主诉过泛、车型目录串、建议没写清、疑似码图、摘要像目录串或「含过程图片记录」、本单 FAQ 空。每条同时给出**改哪里、怎么改**（摘要提示贴在摘要框下）。店员可回去改，也可确认后仍公开。
- 界面只列「问题 + 建议」，不写产品机制、不写「系统将自动优化」。

**与节点确认前检查的关系**：生产时（接车 / 施工 / 完工 / 通知车主前）可先按类目给补图和改句，不硬拦；公开前再扫一遍事实与店页说明。两处都复用已打码图，托管不对同图整单重打。检查与自动脱敏有**总闸 / 套餐闸**（前期全员免费，以后可收费）；关掉后生产步与公开前检查仍可用现有硬拦与托管软建议。详见 [`28_`](../04_维修过程相册/28_节点AI检查_用户关心点与开发计划.md) §4.4、[`26_`](../04_维修过程相册/26_商家端事件节点与单据节点链流程.md)。
