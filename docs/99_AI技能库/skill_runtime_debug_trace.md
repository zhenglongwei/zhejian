# Skill: 运行可观测与约束理解（排障先看迹）

## 目标

遇到「界面不对 / AI 意见缺一块 / 后台行为诡异」时，**先拿到可查的运行痕迹**（输入、输出、错误），再判断是模型、规则还是解析问题；同时**先弄清用户约束的真实意图**，禁止机械执行字面导致空转。

本 skill 来自检测 AI「拆分建议」排障复盘（2026-10-31）：缺大模型原文日志时只能瞎猜；约束被理解成「必须塞满 JSON 某字段」后，提示词空转数小时。

---

## 使用场景

- 大模型/节点 AI：故障分析有了，缺「本单修改」「拆分」「可应用条」等
- 后台链路：打码、识图、归组、审核——结果与预期不符，日志分散或没有落盘
- 用户说「不要程序拼 / 必须模型出 X / 不要合成」——动手前须对齐**防的是什么**
- 同一问题改提示词、补跑、重启后仍复现

不替代具体业务 skill（如 `desensitize-plate-debug`、`merchant-flow-photo-pipeline`）；那些 skill 负责领域步骤，本 skill 负责**排障姿势**与**约束听懂**。

---

## 硬规则

### 1. 先有可查痕迹，再猜根因

| 要查 | 至少落什么 | 说明 |
| --- | --- | --- |
| 输入 | 送出的关键上下文（项 id、槽位、URL 条数、关键开关） | 脱敏后 URL 可与原图分列 |
| 输出 | **模型/服务原文**（截断可接受，须保留关键结构） | 禁止只留「解析后对象」当唯一证据 |
| 解析结果 | 程序最终采用的结构（如 `edits`/`groups`/`status`） | 与原文对照，才能分清「没写」还是「写了被丢掉」 |
| 错误 | 失败原因、空跑次数、超时、引擎切换 | `groupsGap`、补跑 label 等 |

没有上述痕迹时：**优先补落盘/日志**，不要连续改提示词赌运气。

### 2. 约束听意图，不机械执行字面

用户说「必须模型出 groups / 不要程序拼」时，先复述并确认防的是哪一种：

| 用户常想防的 | 可以做的 | 禁止当成 |
| --- | --- | --- |
| 用规则从分析散文里**抽关键词猜检测项名**，导致与修理厂真实会写的**检测项目**不一致 | 模型已给出检测项目名称（如图注 `partName`、明确项目名）时，**程序只做结构化**编成可应用结构 | 「JSON 里某个字段名必须由模型亲手填满，程序绝不能碰结构」 |
| 静默改单据/列表、未点应用就拆项 | 意见区展示建议，点应用再生效 | 把「可应用建议」做成自动写库 |

**`groups` 口径（检测 AI）**：指真实业务中修理厂会写的**检测项目**（一项怎么称呼、怎么挂图），**不一定是「部位名称」**。口头勿把 groups 窄说成「部位名」。

### 3. 分清三层，再动手

```text
① 模型/上游是否已给出业务结论与名称？
② 程序是否缺「结构化 / 映射 / 校验」？
③ 界面是否只认某一字段，导致有结论也显示失败？
```

- ① 没有 → 改提示词、换模型、补图/上下文  
- ① 有、②/③ 缺 → **程序接上**，不要再逼模型重复填同一信息到另一套 JSON 壳里  
- 未分清就改提示词 = 空转高风险

## 落盘约定（backend）

新增或排查涉及外部模型/长链路时，优先采用「最近一次可覆盖落盘」：

| 域 | 建议路径 | 内容 |
| --- | --- | --- |
| 检测节点 AI | `backend/data/inspect-advice-debug/{albumId}-last.json` | traces 原文、attachedSlots、finalEdits、groupsGap |
| 其它 LLM 任务 | `backend/data/<域>-debug/{id}-last.json` 或等价 pm2/文件日志 | 同：输入摘要 + 原文 + 解析结果 + 错误 |
| 脱敏/识图 | 既有 pm2 + smoke；缺则补「本批 id 列表 + 终端状态」 | 见 `desensitize-plate-debug` |
| 原图 403 | access 日志 `GET /api/v1/media/files/...` → `100003` | 权限未过（签名失效且未进相册归属）。**根因口径**：库内禁存 `exp/sig`；挂图即写 `album_images`；读侧重签。草稿=相册编辑态，不是第二媒体对象（见 `26_` §1.0 / `29_` §2） |

要求：

- 落盘失败不影响主流程；debug 目录进 `.gitignore`
- 排障回复里写明：**文件路径、看哪几个字段**
- 用户贴 dump 时，先对照「原文 vs final*」，再下结论

## 排障顺序（默认）

1. **复述用户约束意图**（防猜名？防静默写库？防编造损伤？）——一句说清，不对再问  
2. **找/补运行痕迹**（输入、原文输出、解析结果、错误）  
3. **对照三层**：结论在哪、结构缺哪、界面认哪  
4. **改一处验证一处**；改提示词前须有原文证明「模型确实没给名称/结论」  
5. 交付时说明：搜过哪些入口、日志还在哪、若再复现先打开哪份文件

## 反例（本次空转）

- 无模型原文 → 猜「提示词不够 / 槽位错了」反复补跑  
- 用户「不要程序从意见抽词拼检测项」→ 被执行成「死磕模型填写 `groups:[{…}]`」  
- 模型已在 `imageNotes` 写出检测项目名，且 `groups` 为空壳 → 仍只加提示词，不写「名称认模型、结构程序编」

正例：有 dump → 确认名称已在图注 → 程序按槽合并同名检测项目 → 可应用拆分出成；文档写明禁止用故障分析/检测顺序猜名。

---

## 输出格式（排障时）

默认先报告，用户要求再改代码：

1. **意图对齐**（用户防的是什么 / 不是什么）  
2. **痕迹位置**（路径或「尚无，建议先加」）  
3. **原文要点** vs **解析/界面结果**  
4. **判定落在 ①/②/③ 哪层**  
5. **下一步**（补日志 / 结构化 / 改提示词 / 换入口）——只推一条主路径
