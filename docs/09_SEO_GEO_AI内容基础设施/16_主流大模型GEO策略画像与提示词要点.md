> **生效**：2026-09-10  
> **状态**：一期研究定稿（一次性画像）· 供托管公开「店页文案」LLM 提示词与后续探针迭代  
> **前提**：腾讯 / 阿里 / 豆包等「GEO 工具」**多数无稳定开放 API**；可调用的是大模型推理接口与自建观测。

## 1. 研究结论（给产品与实现的一句话）

| 问题 | 结论 |
| --- | --- |
| 各家 GEO「工具」能否直接 API 接入？ | **现阶段基本不能**。公开能力多为方法论、提示词箱、知识库/RAG 建设、监测看板；不是「传入案例 → 返回 GEO 策略」的官方接口。 |
| 我们能调用什么？ | **大模型 Chat API**（项目已用通义 DashScope 等）+ **自建探针**（`geo-browser-probe`：豆包/通义/元宝网页端 + 搜索引擎）。 |
| 理想「实时跟策略」？ | **做不到官方策略订阅**。可做：**定期探针题库 → 对比引用/提及 → 升提示词版本**（半自动）。 |
| 本期怎么办？ | **一次性画像 → 固化提示词 v0（三家并集）**；探针复测后升 v1/v2。托管页文案用 LLM **只抽可公开面已有事实**，不编造。 |

## 2. 三家公开口径画像（二手公开信息 · 非算法真源）

下列来自厂商社区文章、生态白皮书、第三方 GEO 工具箱描述，**当作「公开叙事与常见做法」**，不作内部权重公式背书。与辙见相关的落点写在右侧。

### 2.1 阿里系（通义 / 百炼 / 云上知识库叙事）

| 公开强调点 | 对辙见案例页的含义 |
| --- | --- |
| 内容要「语义可达」：结构化拆解、摘要 JSON、向量化、知识库入库 | 摘要/FAQ 用**稳定字段**（城市、车型、现象、检查、方案、结果），忌散文口号 |
| 官网/OSS/站长与爬虫可达、Sitemap、权限白名单 | H5 案例页可抓取、Schema、Feed 已有基建继续守住 |
| 二次摘要用大模型抽出「挑战 / 方案 / 价值」类结构 | 托管 GEO 可用 LLM，但**价值句必须能回溯相册**，禁空泛「更安心」 |
| 问答形态、多端分发增加自然问法覆盖 | FAQ **只答本单能核对的题**；空优于编 |

**提示词侧重（阿里向）**：字段齐全、键值清晰、可被切块引用；一段摘要内含齐「谁·车·做了什么·结果」。

### 2.2 腾讯系（混元 / 元宝 / 社区 GEO 工程化叙事）

| 公开强调点 | 对辙见案例页的含义 |
| --- | --- |
| GEO = 面向检索-推理-生成的**信息组织工程**，不是关键词堆砌 | 优先**证据链可读**：检测→方案→施工→结果，而不是 SEO 长尾堆砌 |
| E-E-A-T / 本地权威信源、门店可信 | 来源标「商家上传」；店名/城市/`storeSnapshot`；不写平台背书语 |
| 多模态与结构化治理（图文对齐） | 公开图与文案同指一单；图说与正文不打架 |
| 开源/第三方「GEO 配置助手」多为流程与 Skill，非策略 API | **不依赖**腾讯 GEO 工具 API；元宝侧用探针观测 |

**提示词侧重（腾讯向）**：过程完整、可验证、少绝对化承诺；本地门店语境清楚。

### 2.3 字节系（豆包 / 抖音生态叙事）

| 公开强调点（含第三方白皮书，水分较大） | 对辙见案例页的含义 |
| --- | --- |
| 强调 E-E-A-T、信源梯队、与抖音/头条等内容生态联动 | 我们主战场仍是**案例站公开页**；不幻想「发了抖音就进豆包」自动化 |
| 诊断题库、可见度测试、纠偏、日更/复盘提示词箱 | 与现有 **probe 题库 + 巡检**同构：用题测「会不会被提到」，再改内容 |
| 案例故事、避坑清单、标准化 FAQ 等体裁 | 摘要偏「本单故事」；FAQ 偏「车主会问、本单能答」 |

**提示词侧重（豆包向）**：口语问法 FAQ、本单痛点一句说清、结果可核对；忌广告法风险词。

### 2.4 提示词策略：并集（公倍数），不是公约数

三家要求**无硬冲突，只是各有侧重**。因此 v0 **把三家要点都写进同一套约束**（并集 / 最小公倍数），而不是只保留交集。

| 来源 | 必须写入提示词的侧重 |
| --- | --- |
| **阿里** | 字段齐全、键值清晰、可切块；摘要内尽量齐「城市·车型·项目·现象·检查·方案·结果」；结构稳定便于入库/引用 |
| **腾讯** | 证据链顺序可读（检测→方案→施工→结果）；本地门店实体清楚；可验证、少绝对化承诺；图文同指一单 |
| **豆包** | 本单痛点一句说清；FAQ 用车主口语问法；结果可核对；忌广告法与空话 |

**仍共用的底线**（三家都适用，也是辙见合规底线）：

1. **事实优先**：摘要/亮点只写可公开面已有内容；FAQ **问题**可按类目预置，**答案**须结合本单（可对照行业惯例），薄案例允许空答由商家补。  
2. **对齐规范**：摘要语义对齐 `04_`；FAQ 对齐 `05_`（含空答不上网）。  
3. **信任边界**：不写「已审核」「平台保证修好」；价格合规（公域藏价规则仍有效）。  

**何时才用「公约数」**：仅当某家新要求与另一家或与辙见合规**直接冲突**时，才降级为「取能同时满足的子集」，并记入变更表。当前公开画像下**无此情况**。

## 4. 托管公开 · 店页文案提示词要点（v0 · 三家并集）

> 实现时：system 固化下列**并集**约束；user 只塞**可公开面**（脱敏/自处理后的图注与单据摘要、确认件公开字段），禁止塞原图隐私与内部作业标签。

### 4.1 输入（只允许）

- 城市、门店名（`storeSnapshot`）、服务名、车型（脱敏展示）  
- 主诉 / 检测结论 / 方案要点 / 施工结果 / 质保公开句（若有）  
- 本单已确认 FAQ 候选素材（可空）  
- **不得**输入：完整车牌、手机号、未脱敏原图 URL、商家内部「需处理」档位原文当主文案  

### 4.2 输出 JSON（建议）

```json
{
  "summary": "一段 80–200 字事实摘要",
  "highlights": [{ "label": "车型|项目|检测|方案|结果|门店|…", "value": "短句" }],
  "faq": [{ "q": "车主会怎么问", "a": "本单能核对的答" }]
}
```

约束（并集，全部生效）：

| 维度 | 要求 | 主要对应 |
| --- | --- | --- |
| summary 字段覆盖 | 有则写入：城市、门店、车型、项目、现象、检查、方案、结果；缺则省略不编 | 阿里结构 + `04_` |
| summary 叙事顺序 | 尽量按「现象 → 检查 → 方案 → 结果」组织，可读证据链 | 腾讯过程完整 |
| summary 痛点 | 开头或前半句点明本单要解决的问题（车主话） | 豆包可见度 |
| highlights | ≤6 条；每条 value ≤40 字；键值清晰；须能在输入中找到依据 | 阿里切块 + 腾讯可验证 |
| highlights 建议键 | 至少尽量覆盖：车型、项目、结果；有门店/城市则写入 | 腾讯本地实体 |
| faq | 0–6 条；**口语问法**（按服务类目题库预置）；答可写「惯例→本单→差别」；**薄案例答可空**；禁止「以门店为准」空答；**公开页仅出有答条目** | 豆包 FAQ + `05_` |
| 合规 | 禁止绝对化承诺、好评返现、全网最低、事故车线上估价暗示；不写「已审核」 | 三家信任边界 |

### 4.3 系统提示词骨架（并集版 · 实现时可原样落地）

```
你是汽修公开案例的「可引用文案」写作者：像靠谱老师傅跟车主说话，不是公文、不是营销稿。
根据用户提供的本单可公开事实生成 summary / highlights / faq。
faq 的问题列表由系统按服务类目预置（见 user.faqQuestions），你须按该列表作答：
- 能结合本单写答时：说清「平时常见做法 → 本单怎么做 → 有啥不一样或好处」（若差不多，就说本单按常见规范做的）；严禁编造检测结论、配件、价格、里程。
- 本单几乎无现象/检测/方案等细节时：该条 a 必须为 ""（空字符串），留给商家填写。
严禁广告法话术、空话套话、机器腔（如「旨在」「客观陈述」「因缺少…本说明仅基于…」）。

同时满足下列侧重（无冲突，全部遵守）：
【结构·阿里】摘要尽量覆盖：城市、门店、车型、项目、现象、检查、方案、结果；highlights 用短标签+短值，便于切块引用。
【证据链·腾讯】叙事顺序优先：现象→检查→方案→结果；写清本地门店；过程可核对；禁止绝对化承诺与平台背书语。
【问法·豆包】摘要前半点明本单痛点；faq.q 与预置问保持一致；忌广告法与空话。

语气：专业、简练，同时亲切、友好、像人话。用日常说法，少用书面套话；不卖萌、不堆「亲/呢」，也不要冷冰冰。
摘要、要点 value、faq 答 一律按上述语气。
输出严格 JSON，不要 Markdown。格式：
{"summary":"80-200字","highlights":[{"label":"车型|项目|检测|方案|结果|门店|…","value":"≤40字"}],"faq":[{"q":"与预置问一致","a":"有料则写；薄案例为空串"}]}
highlights ≤6；faq 与 faqQuestions 对齐，条数不超过预置。
禁止绝对化承诺、好评返现、全网最低、事故车线上估价暗示；不写「已审核」。
```

## 5. 从「一次性画像」到「半自动跟策略」

```text
一期（本文件）
  公开资料画像 → 提示词 v0 → 托管页用 LLM 生成店页文案

二期（推荐）
  固定探针题库（城市+项目 / 车型+现象）
  → 定期跑豆包 / 通义 / 元宝（沿用 geo-browser-probe）
  → 人工或半自动对比：是否提及门店/案例要点
  → 修订提示词版本 + 抽样验收

不做（现阶段）
  声称接入腾讯/阿里/豆包「GEO 工具官方 API」
  实时爬取并自动改写全站策略（无授权、不稳定、不可审计）
```
