## 0. 总规则（所有节点共用）

### 0.1 何时跑

店员点「AI分析」才跑。完成施工、发出交车、打开页面都不自动跑。

### 0.2 输入什么（内容优先）

**主口径（按此实现）**：点某一节点的「AI分析」时，模型要看到：

1. **当前节点**的全部实质内容：已写文字 + **尚未识过的图**（打码后送图）；  
2. **之前每一节点**的实质内容：已写文字 + 若该步**已经跑过分析**，只带上那次**分析结果要点**（及每张图第一次识图留下的观察摘要），**不再把旧图文件再送一遍**；若某张图从未识过，这一次才送图并留下观察摘要。

也就是说：**文字与已有分析结论要带齐；图每张一生只交给模型看一次。**

备选轻量口径（暂不采用，除非你改口）：当前节点全文 + 仅前序「分析要点」。信息略少，实现更省。

### 0.3 图只识一次

| 规则 | 说明 |
| --- | --- |
| 第一次 | 打码 → 送模型 → 落库「这张图的观察摘要」（跟图片身份走，不跟第几项） |
| 以后任何节点再用这张图 | 只把观察摘要当文字上下文；**禁止再附图** |
| 打码失败 | 这张不送原图；可标「需人工看图」，不编内容 |
| 本步点「刷新」 | 检测步可再次附上本步全部检测图（便于按图拆项）；刷新后观察摘要以本次为准覆盖 |

### 0.4 意见长什么样

- 按**实质**判断：车主会不会问、做了会不会留证不清、价是否站得住、工序有没有拍到。  
- **禁止**因为「表单填满了 / 有图有字」就输出「这次没有额外意见」这类空话。  
- 若实质已齐、确无风险，输出仍要有一句**对车主价值的确认**（例如「机油与机滤项目清楚，价格在常见区间」），不要空壳。  
- 分两类展示：能写进本步空栏的 →「应用 / 已应用」；不能改已发给车主的单据、只能提醒店员的 → 纯文字。  
- 时间线只摘还要店员动手的一句。

### 0.5 提示词语言

系统提示与用户指令用**英文**写；要求模型 **JSON 字段里的自然语言一律中文**（面向中国汽修店员与车主）。

### 0.6 打码

送模型前必须打码；私密小程序/车主看原图；公开托管只用打码图。

### 1.1 接车（Intake）

**任务**  
留证齐不齐；缺哪侧。不改诉求，不做诊断。

**上下文**  
本步：诉求全文；本步图（均未识则全送；已识则只带摘要）。无前序节点。

**可应用**  
无（不改诉求）。缺侧只提醒补拍。

**展示**  
界面只出一块「还缺这些」（缺哪侧 + 怎么补拍合并成一条）；**不要**再平行展示「还没拍到 / 补一张全景」两块重复文案。解析**优先信 `coverage`**：某侧为 true 即使 `missing` 里写了也不报缺。

**英文提示词**

```
You assist a Chinese auto shop clerk at vehicle intake (pre-repair check-in photos).

Goal: decide whether front / rear / left / right of the car are covered by the photos. Content over form — judge what is actually visible.

Rules:
- Do NOT diagnose damage, severity, or repair order.
- Do NOT rewrite the owner's complaint text.
- Count a side as covered if that side of the car body is clearly visible, including 3/4 angle shots. Perfect square-on panorama is NOT required.
- Only mark a side missing when it is clearly absent from all photos. If unsure, mark it covered (true) and omit it from missing.
- coverage and missing MUST agree: every false in coverage appears in missing; never put a side in missing when coverage says true.
- Output natural-language strings in Simplified Chinese. Keys in English.

Context JSON:
{{CONTEXT}}

Return JSON only:
{
  "coverage": { "front": true|false, "rear": true|false, "left": true|false, "right": true|false },
  "missing": ["车头"|"车尾"|"左侧"|"右侧"],
  "tips": [{ "title": "", "body": "" }],
  "imageNotes": [{ "slot": 1, "note": "short Chinese observation for this photo only" }]
}
```

### 1.2 检测（Inspection）

**任务**  
模型按下面的顺序想，**五步都写进同一个对象**。页面仍只展示故障分析、检测顺序、拆分建议。第 2 步、第 3 步只进调试日志。

1. **故障分析、初步检查顺序只根据接车诉求**，不看检测节点上传的照片。从专业汽修角度，把车主症状的可能原因按可能性从高到低列出（难易可作辅助）。每种可能占一段，用 1、2、3、4 分行。故障分析就写这份完整清单。  
2. **逐张独立看图**，按图1、图2的顺序。前面的图不影响后面的图。只记这张图里实际有的内容，图里没有的损伤不要编。这一步不参考诉求。  
3. **只根据这一张图的内容**判断检测项目。漆面和划痕归划痕检测，底盘照片归底盘检测。不用诉求或第 1 步的句子给照片起名。  
4. 同一条里、语义上同一项目的照片收成一组。结合这一组全部照片，写清说明了什么问题、要不要马上处理、不处理会怎样。看不出后果不要编。不要使用「需处理」「需关注」「状态良好」。不同条里的照片不要并回去。  
5. 用第 4 步的检测项目对照第 1 步的检查顺序。**已经有照片覆盖的项目从检测顺序里去掉**。剩下的才是返回里的检测顺序。都覆盖了，检测顺序用空数组，页面不展示这一块。

**返回对象**（关键字用中文；面向店员的句子用简体中文）

```json
{
  "故障分析": "1. ……\n2. ……",
  "逐张看图": [{ "图": "图1", "内容": "……" }],
  "逐张归类": [{ "图": "图1", "检测项目": "……" }],
  "拆分建议": [
    { "检测项目": "划痕检测", "图片": ["图1", "图2"], "描述": "……" }
  ],
  "检测顺序": ["还没被照片覆盖的那一项"]
}
```

`逐张看图`、`逐张归类` 只写入 `backend/data/inspect-advice-debug/{albumId}-last.json` 的 `steps`，不进意见面板，也不写入检测项。

`图片` 里只放「图1」「图2」这种编号，编号与上下文里的槽位一致。

**命名口径**  
检测项目用店里会开的名称（「划痕检测」「底盘检修」「前制动盘磨损评估」都可以）。不要用光秃秃的「车门」「刹车」顶替，也不要把检测顺序的句子抄成项目名。语义归并由模型做完；程序不把「划痕」和「划痕检测」猜成同一项。模型若对同一条检测项写出了完全相同的项目名，程序只把这些图收进同一组。

**上下文（只作输入）**  
- 接车：诉求 + 接车留证要点 + 接车图观察摘要（**不重附图**）  
- 本步：全部检测项文字；本步未识检测图送模；已识图只带摘要  
- 每张检测图的槽位号，以及它现在属于哪一条检测项（供模型只在同一条里归并；返回里不要抄项 id）

**禁止输出**  
接车留证句（如「车身四周都拍到了 / 还缺某侧」）；英文单词或英文缩写出现在面向店员的自然语言里；部件参考；项 id；空拆分再补跑。逐张看图和逐张归类不得上屏。

**展示三块**  
1. 故障分析（只读）：诉求下的可能原因，一段一条。  
2. 检测顺序（只读）：照片还没覆盖的检查项。都覆盖了则不出这一块。  
3. 拆分建议：每组写出检测项目、对应图（图N）、描述。一组也展示。两组及以上才出现「应用」，点了才改节点。故障分析有内容即算出成。

**对象**  
检测项身份 = 项 `id`。模型不写这个 id。程序用「图N」对上槽位，再挂回该图已经属于的那一条。同一条里两组及以上才出现应用条。应用后按组拆成多项并写入各组描述；没被分到的图仍留在原项。已有字不覆盖。  
**硬闸**：出意见、刷新、轮询加载都只更新意见面板；**禁止**据此改 `photoDraft.findings`。检测项列表只在店员点「应用」后变化。  
**解析**：页面只认故障分析、检测顺序、拆分建议（并兼容同义的旧键，避免模型偶发用了旧键就整段空白）。`逐张看图`、`逐张归类` 只进调试日志，不参与上屏，也不用来补拆分。`图片` 认「图N」和数字。一组缺检测项目名、或编号对不上已有照片，丢掉这一组，不影响另外两组。不根据故障分析、检测顺序或逐张看图猜项目名。

**提示词**（检测这一步整段用中文。其它节点仍用英文指令。）

```

按下面五步思考，五步的结果都写进这一个 JSON。

1. 故障分析只根据接车时的客户诉求，不要看这次上传的检测照片。
从专业汽修的角度，把这个症状所有可能的原因列出来，按可能性从高到低排。
每种可能占一段，用1、2、3、4分行。写入「故障分析」。

2. 再单独看照片。按图1、图2的顺序，每张图独立看，前面的图不影响后面的图。

4. 把同一条里、语义上属于同一检测项目的照片分成一组。

已经分在不同条里的照片不要并到一起。写入「拆分建议」。

5. 用第4步得到的检测项目，对照第1步那份清单。
已经有照片覆盖的项目，从清单里去掉。剩下的写入「检测顺序」，仍然一段一项。
如果照片已经把第1步的可能都覆盖了，检测顺序用空数组。

不要复述接车时车身四周有没有拍全。
参考材料只给第1步用。给照片归类时不要用它。
```

### 1.3 报价（Quote）/ 补充报价（Addon quote）

**任务**  
结合检测意见，给出按项的 **报价参考**（参考价 + 报价原因/必要性）和 **建议补充**。必要性即回答车主「为什么要做」，不单开「车主可能问」。施工怎么拍不在本步。

**上下文**  
- 检测意见：故障分析、检测顺序（含原先写在部件参考里的注意点）、拆分建议要点  
- 接车诉求摘要  
- 本步报价表（有则对齐现有行；空则出建议行）  

**展示**  
1. **报价参考**：每项名称、参考价档、报价原因；`optional=true` 时标「可由车主选择」。表上还没有的项旁 **应用** → 只写入项目名（品牌/金额/参考价不进表）；写上后 **已应用**。已有同名行无应用。  
2. **建议补充**：检测有依据、表上没有的；可 **应用** 加一行同名（只写项目名）。分析完成不静默改表。  

**参考价分型**  
- `parts`：oem / brand / economy  
- `labor`：dealer（4S）/ indie（修理厂）  

**英文提示词**

```
You assist a Chinese auto shop clerk on the quote step.

Goal: using inspection advice + current quote lines, produce per-line quote reference (bands + reason) and optional supplements. Necessity IS the reason field — do NOT output a separate owner-FAQ block. Do NOT output workmanship photo plans (that belongs to the work step).

Hard rules:
- Use inspectionAdvice as context; do not restate intake coverage.
- If quote lines exist, one suggestedLines row per existing line (same name). If empty, propose lines from inspection (amounts stay empty).
- kind=parts → oem/brand/economy ranges. kind=labor → dealer/indie ranges.
- reason: why quote this now, in shop-clerk Chinese; for watch/optional items set optional=true and say owner may choose.
- supplements: inspection-backed items missing from the table; remind only.
- Simplified Chinese only in natural-language values. Accident cars: leave all bands empty.

Context JSON:
{{CONTEXT}}

Return JSON only:
{
  "suggestedLines": [{ "name": "", "note": "", "kind": "parts|labor", "oem": "", "brand": "", "economy": "", "dealer": "", "indie": "", "reason": "", "optional": false }],
  "omissions": [{ "title": "", "body": "" }]
}
```

### 1.4 施工（Work）

## 2. 图片与报告：产品口径 vs 实现偏差

### 2.1 正确产品口径（嵌套真源）

与 [`26_`](./26_商家端事件节点与单据节点链流程.md) §1.0、[`15_`](../01_项目总览与业务架构/15_案例档案与托管状态机.md) §1.0 同一条不变量。

> **修订**：2026-10-31 · **草稿 = 相册编辑态**；**节点 = 阶段**；**报告 = 由已结束节点 `content` 派生的只读件**。废止 `photoDraft` / `document.payload` 双真源；挂图统一归属相册；库内不存签名。

```
案例相册（编辑态 → 全节点结束完结 → 可托管）
  → 节点 content（唯一内容袋；挂图进 album_images）
  → 节点已结束 → 报告（接车/检测/报价/工单/交车）= content 只读派生
  → 车主 / 托管 / 摘要·FAQ = 只认派生报告
```

- **草稿不是第二对象**，是整本相册完结前的编辑状态。  
- **节点一份 `content`**：商家图+文写进这里；兼容期可读旧 `photoDraft`，落盘只写 `content`。  
- **报告由 content 派生**：`document` 仅信封（docType/status/时间）；禁止再拷贝一套 findings/photos 当真源。  
- **本单图库：已确认删除**；归属索引保留以便原图可读。  
- **原图读**：持久化裸 URL；读 API 重签；权限 = 签名有效 **或** 已归属本相册。

### 2.2 实现债（应收口）

| 偏差 | 收口 |
| --- | --- |
| `photoDraft` 与 `document.payload` 两套业务字段 | 合并进 `content`；报告 view 派生；信封只留状态 |
| 进行中图未进 `album_images` | 挂图即 upsert；读 flow 补登记 |
| 库内 URL 带过期 `exp`/`sig` | 落盘剥查询串；读出口重签 |

**收口原则**

1. 节点内容真源只有 `content`；发出/结束只改信封状态并冻结 content。  
2. 报告正文 = 对 content 的投影，不是第二份文件。  
3. 车主 / 商家预览 / 托管：已结束只认派生报告。  
4. 本单图库已删；挂图归属始终是相册。

## 3. 状态流转（2026-10-27 定稿）

主链：接车发出 → 检测报告发出 → 报价发出并**车主确认（或代确认）** → 施工 → 交车发出 → 车主确认交车。

### 3.1 三条闸门

1. **顺序**：上一个大步完成之后，才能进入下一个大步作业。未到的步不能跳进去改。  
2. **发出即冻**：该步单据**一旦发给车主**（`pending_confirm` / `delivered` / `confirmed` 均算），**不必等车主点确认**，该步及之前各步一律只读可看、不可改。发出之前，可以退回上一步修改。  
   - 接车发出 → 接车冻；在检测中不能改接车。  
   - 检测报告发出 → 检测+接车冻；在报价中不能改检测/接车。  
   - 报价发出 → 报价+更早冻；在施工中不能改报价及更早。  
   - **交车报告发出** → 施工及更早全部冻。交车发出前，仍可从交车退回施工补图/说明，也可开补充报价。  
3. **补充报价**：施工中发现未报价项可新增补充报价 → 待车主确认或商家代确认 → **回到施工**继续。补充单发出后该张补充单本身也冻（同「发出即冻」）。

### 3.2 冻结与完成的区别

| 概念 | 含义 |
| --- | --- |
| 发出即冻 | 商家不能再改这一步（及更早）的内容 |
| 步完成 / 解锁下一步 | 接车完成进检测；检测报告发出进报价；**报价须确认**才进施工；施工完成进交车；交车发出等车主确认 |
