## 0. 总规则（所有节点共用）

### 0.1 何时跑

店员点「AI分析」才跑。完成施工、发出交车、打开页面都不自动跑。

### 0.2 输入什么（内容优先）

**主口径（按此实现）**：点某一节点的「AI分析」时，模型要看到：

1. **当前节点**的全部实质内容：已写文字 + **尚未识过的图**（打码后送图）；  
2. **之前每一节点**的实质内容：已写文字 + 若该步**已经跑过分析**，只带上那次**分析结果要点**（及每张图第一次识图留下的观察摘要），**不再把旧图文件再送一遍**；若某张图从未识过，这一次才送图并留下观察摘要。

也就是说：**文字与已有分析结论要带齐；图每张一生只交给模型看一次。**

备选轻量口径（暂不采用，除非你改口）：当前节点全文 + 仅前序「分析要点」。信息略少，实现更省。

### 0.3 图只识一次

| 规则 | 说明 |
| --- | --- |
| 第一次 | 打码 → 送模型 → 落库「这张图的观察摘要」（跟图片身份走，不跟第几项） |
| 以后任何节点再用这张图 | 只把观察摘要当文字上下文；**禁止再附图** |
| 打码失败 | 这张不送原图；可标「需人工看图」，不编内容 |

### 0.4 意见长什么样

- 按**实质**判断：车主会不会问、做了会不会留证不清、价是否站得住、工序有没有拍到。  
- **禁止**因为「表单填满了 / 有图有字」就输出「这次没有额外意见」这类空话。  
- 若实质已齐、确无风险，输出仍要有一句**对车主价值的确认**（例如「机油与机滤项目清楚，价格在常见区间」），不要空壳。  
- 分两类展示：能写进本步空栏的 →「应用 / 已应用」；不能改已发给车主的单据、只能提醒店员的 → 纯文字。  
- 时间线只摘还要店员动手的一句。

### 0.5 提示词语言

系统提示与用户指令用**英文**写；要求模型 **JSON 字段里的自然语言一律中文**（面向中国汽修店员与车主）。

### 0.6 打码

送模型前必须打码；私密小程序/车主看原图；公开托管只用打码图。

### 1.1 接车（Intake）

**任务**  
留证齐不齐；缺哪侧。不改诉求，不做诊断。

**上下文**  
本步：诉求全文；本步图（均未识则全送；已识则只带摘要）。无前序节点。

**可应用**  
无（不改诉求）。缺侧只提醒补拍。

**展示**  
界面只出一块「还缺这些」（缺哪侧 + 怎么补拍合并成一条）；**不要**再平行展示「还没拍到 / 补一张全景」两块重复文案。解析**优先信 `coverage`**：某侧为 true 即使 `missing` 里写了也不报缺。

**英文提示词**

```
You assist a Chinese auto shop clerk at vehicle intake (pre-repair check-in photos).

Goal: decide whether front / rear / left / right of the car are covered by the photos. Content over form — judge what is actually visible.

Rules:
- Do NOT diagnose damage, severity, or repair order.
- Do NOT rewrite the owner's complaint text.
- Count a side as covered if that side of the car body is clearly visible, including 3/4 angle shots. Perfect square-on panorama is NOT required.
- Only mark a side missing when it is clearly absent from all photos. If unsure, mark it covered (true) and omit it from missing.
- coverage and missing MUST agree: every false in coverage appears in missing; never put a side in missing when coverage says true.
- Output natural-language strings in Simplified Chinese. Keys in English.

Context JSON:
{{CONTEXT}}

Return JSON only:
{
  "coverage": { "front": true|false, "rear": true|false, "left": true|false, "right": true|false },
  "missing": ["车头"|"车尾"|"左侧"|"右侧"],
  "tips": [{ "title": "", "body": "" }],
  "imageNotes": [{ "slot": 1, "note": "short Chinese observation for this photo only" }]
}
```

### 1.2 检测（Inspection）

**任务**  
结合接车诉求/分析要点与本步检测项、图，给出：**故障分析**、**检测顺序**、**部件参考**，以及对已上传检测图/文的**修改建议**（补图、拆项、补写/改写部位名与检查发现）。

**上下文（只作输入）**  
- 接车：诉求 + 接车留证要点 + 接车图观察摘要（**不重附图**）  
- 本步：全部检测项文字；本步未识检测图送模；已识图只带摘要  

**禁止输出**  
接车留证句（如「车身四周都拍到了 / 还缺某侧」）；英文单词或英文缩写出现在面向店员的自然语言里。

**展示四块**  
1. 故障分析（只读）  
2. 检测顺序（只读）  
3. 部件参考（只读）  
4. 本单修改（可应用）：**每个检测项至多一条**；图+文打包。混在一起要拆 → 一条里同时给 `groups`（每组图+部位名+检查发现），点一次应用即拆好并写上字；已拆开 → 按项各一条（要不要再拆、要不要改文案都在这一条）。`photo` 补拍只文字无应用。

**对象**  
检测项身份 = 项 `id`。一条意见对应一个 `findingId`。应用：有 `groups`（≥2）则拆成多项并写入各组文案；否则只填该项空着的部位名/检查发现。已有字不覆盖。

**英文提示词**

```
You assist a Chinese auto shop clerk during vehicle inspection.

Goal: faultAnalysis, inspectOrder, partHints, and ONE actionable edit per current inspection finding (photos + text together).

Hard rules:
- Intake coverage is CONTEXT ONLY — never restate it in output.
- Simplified Chinese only in natural-language values. No English words.
- Do NOT invent damage absent from photos/text. No internal labels 需处理 / 需关注 / 状态良好 in sentences.
- edits: at most ONE row per findingId. If photos in that finding should be split, put split+text in the SAME row (groups with partName, advice, imageSlots). If already one topic, fill partName/advice on that findingId without groups. kind=photo is reminder only (no apply).
- partHints are read-only.

Context JSON:
{{CONTEXT}}

Return JSON only:
{
  "faultAnalysis": "中文，一两句",
  "inspectOrder": ["先查…", "再查…"],
  "partHints": [{ "title": "部位", "body": "为何要看 / 看什么" }],
  "edits": [
    { "kind": "item", "findingId": "", "partName": "", "advice": "", "body": "给店员看的一句", "groups": [{ "partName": "", "advice": "", "imageSlots": [1] }] },
    { "kind": "photo", "findingId": "", "body": "建议补拍…" }
  ],
  "imageNotes": [{ "slot": 1, "note": "中文观察" }]
}
```

### 1.3 报价（Quote）/ 补充报价（Addon quote）

**任务（消费者关心）**  
项目是否必要；是否漏关键项；价格是否合理；施工时应拍哪些工序照（提醒商家）。

**上下文**  
- 接车分析要点 + 图摘要  
- 检测分析要点 + 图摘要 + 检测关键文字  
- 本步：当前报价表每一行（名称、品牌、**金额**）；补充报价时加上新发现说明/图（未识才附图）  

**硬规则**  
表上**没有的行不要当本单事实**（删了拆检就不要讲拆检收费）。必须审金额是否离谱。

**可应用**  
建议漏项名称（金额空）——点应用再加行（可选）。不自动改金额。

**英文提示词**

```
You assist a Chinese auto shop clerk reviewing a repair quote (or a mid-work addon quote).

Goal: necessity of lines, missing critical lines, price reasonableness, and which workmanship photos the shop should take later. Content over form. Never claim "no issues" only because the table has rows.

The CURRENT quote table is ground truth. Do NOT discuss items that are not on the table.
You MUST review every filled amount for being absurdly high or low for that service in a normal China independent shop; call out outliers explicitly.
Do NOT change amounts. Do NOT turn common industry talk into billable lines.
For addon quotes: explain why this was not on the first quote, tied to new findings/photos.

Prior steps: intake + inspection summaries and image notes only (no re-attach old images).
Current: full quote lines with amounts; new photos only if not yet noted.

Context JSON:
{{CONTEXT}}

Return JSON only:
{
  "priceIssues": [{ "lineName": "", "body": "Chinese: why the price looks off and how to explain to owner" }],
  "omissions": [{ "title": "", "body": "", "suggestAdd": true }],
  "necessity": [{ "lineName": "", "body": "Chinese: why needed or why optional" }],
  "photoPlan": [{ "title": "", "body": "Chinese: which process photos to take during work" }],
  "objections": [{ "ask": "", "heard": "", "ours": "", "say": "" }],
  "imageNotes": [{ "slot": 1, "note": "" }]
}
```

### 1.4 施工（Work）

**任务（消费者关心）**  
关键工序有没有拍到；配件品牌有没有；新旧件对比有没有；说明是否够车主看懂。

**上下文**  
- 接车 / 检测 / 报价（及已确认补充报价）的分析要点与图摘要  
- 本步：施工每一项名称、说明、挂图；**未识**施工图送模  

**可应用**  
空说明 + 有图 → 一句可写入的施工描述；图挂错项 → 建议挪到已有项（点应用才挪）。

**只提醒**  
报价有施工无；施工有报价无（旁链补充报价）；缺品牌/新旧对比/关键工序照。

**英文提示词**

```
You assist a Chinese auto shop clerk during repair work documentation.

Goal: whether critical process photos exist, brand/spec of parts, old-vs-new comparison, and whether captions are clear for the car owner. Content over form — empty captions or missing process evidence are problems even if "some photos were uploaded".

Compare against confirmed quote lines. Do NOT change prices.
Prior steps: use analysis summaries + image notes only; do not re-attach those images.
Current: work items and NEW work photos only.

Owner cares about proof of work, what was replaced, and readable descriptions — not technician poses or tool close-ups.

Context JSON:
{{CONTEXT}}

Return JSON only:
{
  "gaps": [{ "kind": "missing_quote_item|extra_work|missing_process_photo|missing_brand|missing_old_new", "title": "", "body": "" }],
  "items": [{ "id": "", "body": "Chinese caption suitable to write into empty work note", "canApply": true }],
  "groups": [{ "slot": 1, "partName": "must be an existing work item name", "body": "" }],
  "imageNotes": [{ "slot": 1, "note": "" }]
}
```

### 1.5 交车（Delivery）— 全流程综合 + 公开说明草稿

**任务（两段，同一次请求）**

1. **对账（给店员）**：把接车→检测→报价→施工→交车**整链看一遍**（用各步分析要点 + 本步交车图/质保）。车主已看过的单据只能指出问题、不能改；能改的只有本步交车草稿。对账意见**不进公开案例**。  
2. **公开说明草稿（给车主可读 + 托管复用）**：基于同一份全案事实，写 **摘要 + FAQ**（GEO 可引用、言之有物、消费者关心）。写入相册 `archiveCopy`，见 `15_` §6.1 / `17_` §0。

**上下文**  
全链路分析要点 + 各图观察摘要 + 单据链事实包；本步未识交车图；质保字段。**送模前**文字洗掉车牌 / VIN / 姓名 / 手机号；图只用已打码或图说。

**可应用**  
- 对账：仅本步空质保期限、空注意事项等。  
- 草稿：落相册 `archiveCopy`，不写进交车报告字段。

**英文提示词**

```
You assist a Chinese auto shop clerk at vehicle delivery / handover.
```

## 2. 图片与报告：产品口径 vs 实现偏差

### 2.1 正确产品口径（嵌套真源）

与 [`26_`](./26_商家端事件节点与单据节点链流程.md) §1.0、[`15_`](../01_项目总览与业务架构/15_案例档案与托管状态机.md) §1.0 同一条不变量：

```
案例相册
  → 节点草稿（进行中）
  → 发出/确认定稿 → 报告自带当时的图与字（报告属性）
  → 车主 / 托管 / 摘要·FAQ = 只脱胎自定稿（禁止草稿兜底拼装）
```

- **草稿不是第二份稿**，只是同一条内容在「未定稿」时的状态。  
- 定稿后，图跟着**报告**走，不该再从别处「拼一张回来」。  
- 挂图位置：接车 = 节点 `pendingImages` → 定稿写入报告 `photos`；检测/工单 = 项对象 `images[]` → 定稿写入报告发现项/施工项。  
- **本单图库：已确认删除**。删项只从本步拿掉挂图关系；文件可留对象存储。

### 2.2 实现债（应收口，不是产品要两套稿）

| 偏差 | 收口 |
| --- | --- |
| 接车发出未稳定写入 `document.payload.photos`，读侧回落草稿 | 发出/更新接车单据时强制从 `pendingImages` 写入；已定稿禁止回落 |
| 检测报告有时只带文字，图仍只在草稿 / 旧阶段散图拼项 | 定稿以草稿 `findings`（含挂图）为唯一真源，`strictFindings` |
| 工单读侧拼 `photoDraft` | 完成时写入 `document.payload.workItems`；已完成只读定稿 |
| 交车选图与报告漏拷 | 定稿只认草稿外观+勾选 URL，一次写入 `deliveryPhotos` |
| 托管/脱敏另建名单 | 事实包与脱敏名单脱胎定稿报告属性 |

**收口原则**

1. 每份对外报告定稿瞬间：把采用的图 URL **写入该报告 payload（工单为 workItems）并以此为唯一读源**。  
2. 草稿态与定稿态是同一对象的状态，不是两份平行文件。  
3. 车主端、商家预览、托管通读：**已定稿只读报告属性**；缺图暴露为缺图，不回落草稿。  
4. **本单图库已删除**；脱敏/托管名单只从各步报告（进行中才允许本步草稿挂图）收集。

## 3. 状态流转（2026-10-27 定稿）

主链：接车发出 → 检测报告发出 → 报价发出并**车主确认（或代确认）** → 施工 → 交车发出 → 车主确认交车。

### 3.1 三条闸门

1. **顺序**：上一个大步完成之后，才能进入下一个大步作业。未到的步不能跳进去改。  
2. **发出即冻**：该步单据**一旦发给车主**（`pending_confirm` / `delivered` / `confirmed` 均算），**不必等车主点确认**，该步及之前各步一律只读可看、不可改。发出之前，可以退回上一步修改。  
   - 接车发出 → 接车冻；在检测中不能改接车。  
   - 检测报告发出 → 检测+接车冻；在报价中不能改检测/接车。  
   - 报价发出 → 报价+更早冻；在施工中不能改报价及更早。  
   - **交车报告发出** → 施工及更早全部冻。交车发出前，仍可从交车退回施工补图/说明，也可开补充报价。  
3. **补充报价**：施工中发现未报价项可新增补充报价 → 待车主确认或商家代确认 → **回到施工**继续。补充单发出后该张补充单本身也冻（同「发出即冻」）。

### 3.2 冻结与完成的区别

| 概念 | 含义 |
| --- | --- |
| 发出即冻 | 商家不能再改这一步（及更早）的内容 |
| 步完成 / 解锁下一步 | 接车完成进检测；检测报告发出进报价；**报价须确认**才进施工；施工完成进交车；交车发出等车主确认 |
