## 0. 总规则（所有节点共用）

### 0.1 何时跑

店员点「AI分析」才跑。完成施工、发出交车、打开页面都不自动跑。

### 0.2 输入什么（内容优先）

**主口径（按此实现）**：点某一节点的「AI分析」时，模型要看到：

1. **当前节点**的全部实质内容：已写文字 + **尚未识过的图**（打码后送图）；  
2. **之前每一节点**的实质内容：已写文字 + 若该步**已经跑过分析**，只带上那次**分析结果要点**（及每张图第一次识图留下的观察摘要），**不再把旧图文件再送一遍**；若某张图从未识过，这一次才送图并留下观察摘要。

也就是说：**文字与已有分析结论要带齐；图每张一生只交给模型看一次。**

备选轻量口径（暂不采用，除非你改口）：当前节点全文 + 仅前序「分析要点」。信息略少，实现更省。

### 0.3 图只识一次

| 规则 | 说明 |
| --- | --- |
| 第一次 | 打码 → 送模型 → 落库「这张图的观察摘要」（跟图片身份走，不跟第几项） |
| 以后任何节点再用这张图 | 只把观察摘要当文字上下文；**禁止再附图** |
| 打码失败 | 这张不送原图；可标「需人工看图」，不编内容 |
| 本步点「刷新」 | 检测步可再次附上本步全部检测图（便于按图拆项）；刷新后观察摘要以本次为准覆盖 |

### 0.4 意见长什么样

- 按**实质**判断：车主会不会问、做了会不会留证不清、价是否站得住、工序有没有拍到。  
- **禁止**因为「表单填满了 / 有图有字」就输出「这次没有额外意见」这类空话。  
- 若实质已齐、确无风险，输出仍要有一句**对车主价值的确认**（例如「机油与机滤项目清楚，价格在常见区间」），不要空壳。  
- 分两类展示：能写进本步空栏的 →「应用 / 已应用」；不能改已发给车主的单据、只能提醒店员的 → 纯文字。  
- 时间线只摘还要店员动手的一句。

### 0.5 提示词语言

系统提示与用户指令用**英文**写；要求模型 **JSON 字段里的自然语言一律中文**（面向中国汽修店员与车主）。

### 0.6 打码

送模型前必须打码；私密小程序/车主看原图；公开托管只用打码图。

### 1.1 接车（Intake）

**任务**  
留证齐不齐；缺哪侧。不改诉求，不做诊断。

**上下文**  
本步：诉求全文；本步图（均未识则全送；已识则只带摘要）。无前序节点。

**可应用**  
无（不改诉求）。缺侧只提醒补拍。

**展示**  
界面只出一块「还缺这些」（缺哪侧 + 怎么补拍合并成一条）；**不要**再平行展示「还没拍到 / 补一张全景」两块重复文案。解析**优先信 `coverage`**：某侧为 true 即使 `missing` 里写了也不报缺。

**英文提示词**

```
You assist a Chinese auto shop clerk at vehicle intake (pre-repair check-in photos).

Goal: decide whether front / rear / left / right of the car are covered by the photos. Content over form — judge what is actually visible.

Rules:
- Do NOT diagnose damage, severity, or repair order.
- Do NOT rewrite the owner's complaint text.
- Count a side as covered if that side of the car body is clearly visible, including 3/4 angle shots. Perfect square-on panorama is NOT required.
- Only mark a side missing when it is clearly absent from all photos. If unsure, mark it covered (true) and omit it from missing.
- coverage and missing MUST agree: every false in coverage appears in missing; never put a side in missing when coverage says true.
- Output natural-language strings in Simplified Chinese. Keys in English.

Context JSON:
{{CONTEXT}}

Return JSON only:
{
  "coverage": { "front": true|false, "rear": true|false, "left": true|false, "right": true|false },
  "missing": ["车头"|"车尾"|"左侧"|"右侧"],
  "tips": [{ "title": "", "body": "" }],
  "imageNotes": [{ "slot": 1, "note": "short Chinese observation for this photo only" }]
}
```

### 1.2 检测（Inspection）

**任务**  
三块必须分开写，禁止互相顶替：

1. **故障诊断**（`faultAnalysis`，只读）：结合诉求与检测图，写看见了什么、可能是什么问题。  
2. **检测顺序**（`inspectOrder`，只读）：按**客户诉求**列出建议检查路径（先查什么、再查什么）。**不是**把已上传的图拆成多项。  
3. **拆分建议**（`edits[].groups`，可应用）：只根据**商家已上传的检测图**。一项里的图若明显属于不同检测项目，才给出拆分：每组须有修理厂真实会写的**检测项目名称**、对应图片（`imageSlots` / 图N）、检测原因或注意点（`advice`）。点「应用」才改节点内容。图同属一项、不必拆时，**不要**出 `groups`，文本意见仍算出成。

**命名口径**：拆分后的每一项名称须是模型根据真实修车场景写出的检测项目（如「前制动盘磨损评估」「左后门下沿钣喷」），**禁止**用笼统部位（「车门」「刹车」）或工序词顶替，也**禁止**把检测顺序条目抄成拆分名称。

**上下文（只作输入）**  
- 接车：诉求 + 接车留证要点 + 接车图观察摘要（**不重附图**）  
- 本步：全部检测项文字；本步未识检测图送模；已识图只带摘要  

**禁止输出**  
接车留证句（如「车身四周都拍到了 / 还缺某侧」）；英文单词或英文缩写出现在面向店员的自然语言里。

**展示四块**  
1. 故障分析（只读）  
2. 检测顺序（只读）  
3. 部件参考（只读）  
4. 本单修改（可应用）：**每个检测项至多一条**；图+文打包。混在一起要拆 → 一条里同时给 `groups`（每组图+**检测项目名称**+检查发现），点一次应用即拆好并写上字；已拆开 → 按项各一条（要不要再拆、要不要改文案都在这一条）。`photo` 补拍只文字无应用。

**对象**  
检测项身份 = 项 `id`。一条意见对应一个 `findingId`。应用：有 `groups`（≥2）则拆成多项并写入各组文案；否则只填该项空着的检测项目名/检查发现。已有字不覆盖。  
**硬闸**：出意见、刷新、轮询加载都只更新意见面板；**禁止**据此改 `photoDraft.findings`。检测项列表只在店员点「应用」后变化。  
**解析兜底**：`findingId` 必须对得上真实项 id；若模型写错（如照抄示例 `pile`）且全单**恰好只有一个**多图项，解析层重挂到该 id。`imageSlots` 认数字与「图N」。多个多图项时错误 id 不猜，避免串项。

**英文提示词**（指令用英文；JSON 里面向店员的字符串用简体中文）

```
You assist a Chinese auto-shop clerk on the inspection step.

Output four blocks: faultAnalysis, inspectOrder, partHints, edits (+ imageNotes).

CRITICAL — photo split (groups):
1. Look at every attached image (slot numbers in photoSlots / newPhotoSlots).
2. Decide which shop inspection LINE each slot belongs to (what a Chinese repair shop would write as a检测项目 on the job sheet).
3. Naming: groups[].partName and imageNotes[].partName are **inspection line names used in real shops**, NOT required to be anatomic body-part labels only. Prefer names like「前制动盘磨损评估」「左后门下沿钣喷」; avoid bare「车门」「刹车」unless that is how the shop actually names the line.
4. If one findingId owns 2+ slots with DIFFERENT inspection lines, you MUST emit one edits[] row for that findingId with groups[]:
   - one group per inspection line
   - each group: partName (line name), advice, imageSlots
   - every slot of that findingId appears in exactly one group
5. inspectOrder is the check path from the owner complaint. It is NOT a photo-split plan. Never copy inspectOrder lines into groups[].partName.
6. Omit groups when uploaded photos of that finding are the SAME inspection line (text-only opinion is success). Do NOT invent a split because faultAnalysis has 1. 2. 3.
7. findingId in edits MUST be copied exactly from Context items[].id or photoSlots[].findingId. Never invent placeholders like "pile".
8. imageSlots must be numeric slot ids from photoSlots (e.g. 1, 2, 3).

REQUIRED split checks: for each multi-photo findingId, if its slots show different inspection lines, emit one edits row covering every listed slot.

Example when finding "{{REAL_FINDING_ID}}" has different inspection lines across its slots:
"edits": [{
  "kind": "item",
  "findingId": "{{REAL_FINDING_ID}}",
  "body": "拆成左后门下沿钣喷、前制动盘磨损评估、底盘锈蚀检查",
  "groups": [
    { "partName": "左后门下沿钣喷", "advice": "…", "imageSlots": [1] },
    { "partName": "前制动盘磨损评估", "advice": "…", "imageSlots": [2] },
    { "partName": "底盘锈蚀检查", "advice": "…", "imageSlots": [3] }
  ]
}]

Other rules:
- Intake text is context only — never restate intake coverage.
- Natural-language JSON values: Simplified Chinese only (no English words).
- Do not invent damage not in photos/text. No labels 需处理 / 需关注 / 状态良好.
- imageNotes: short per-slot observation; partName = same inspection-line naming rule; never a substitute for groups.
- kind=photo edits are reminders only (no apply).

Context JSON:
{{CONTEXT}}

Return JSON only with keys: faultAnalysis, inspectOrder, partHints, edits, imageNotes.
```

**结构化与补跑（名称认模型，结构程序可补）**
- 合格 `edits.groups` 优先用模型直接写的；空壳 `[{},{}]` 不算。
- 若模型同轮已在 `imageNotes` 里按槽写了 **不同** `partName`（检测项目名称），解析层**只做结构化**：同名槽合并为一组，`advice` 取该槽 `note`，编成可应用 `groups`。**禁止**用故障分析分点、检测顺序、规则词表猜检测项名称或按槽硬拆。
- 模型已写空壳 `groups` 或图注已命名却未编成结构时，带着图英文补跑（最多两次）只补 `groups`。故障分析/检测顺序分了点 **不等于** 必须拆图，不得因此判失败。
- 不必拆时：意见以故障诊断 + 检测顺序文本为准，算出成；不出现拆分应用条。未点应用仍不改检测项列表。

### 1.3 报价（Quote）/ 补充报价（Addon quote）

**任务**  
结合检测意见，给出按项的 **报价参考**（参考价 + 报价原因/必要性）和 **建议补充**。必要性即回答车主「为什么要做」，不单开「车主可能问」。施工怎么拍不在本步。

**上下文**  
- 检测意见：故障分析、检测顺序、部件参考、本单修改要点  
- 接车诉求摘要  
- 本步报价表（有则对齐现有行；空则出建议行）  

**展示**  
1. **报价参考**：每项名称、参考价档、报价原因；`optional=true` 时标「可由车主选择」。表上还没有的项旁 **应用** → 只写入项目名（品牌/金额/参考价不进表）；写上后 **已应用**。已有同名行无应用。  
2. **建议补充**：检测有依据、表上没有的；可 **应用** 加一行同名（只写项目名）。分析完成不静默改表。  

**参考价分型**  
- `parts`：oem / brand / economy  
- `labor`：dealer（4S）/ indie（修理厂）  

**英文提示词**

```
You assist a Chinese auto shop clerk on the quote step.

Goal: using inspection advice + current quote lines, produce per-line quote reference (bands + reason) and optional supplements. Necessity IS the reason field — do NOT output a separate owner-FAQ block. Do NOT output workmanship photo plans (that belongs to the work step).

Hard rules:
- Use inspectionAdvice as context; do not restate intake coverage.
- If quote lines exist, one suggestedLines row per existing line (same name). If empty, propose lines from inspection (amounts stay empty).
- kind=parts → oem/brand/economy ranges. kind=labor → dealer/indie ranges.
- reason: why quote this now, in shop-clerk Chinese; for watch/optional items set optional=true and say owner may choose.
- supplements: inspection-backed items missing from the table; remind only.
- Simplified Chinese only in natural-language values. Accident cars: leave all bands empty.

Context JSON:
{{CONTEXT}}

Return JSON only:
{
  "suggestedLines": [{ "name": "", "note": "", "kind": "parts|labor", "oem": "", "brand": "", "economy": "", "dealer": "", "indie": "", "reason": "", "optional": false }],
  "omissions": [{ "title": "", "body": "" }]
}
```

## 2. 图片与报告：产品口径 vs 实现偏差

## 3. 状态流转（2026-10-27 定稿）

主链：接车发出 → 检测报告发出 → 报价发出并**车主确认（或代确认）** → 施工 → 交车发出 → 车主确认交车。

### 3.1 三条闸门

1. **顺序**：上一个大步完成之后，才能进入下一个大步作业。未到的步不能跳进去改。  
2. **发出即冻**：该步单据**一旦发给车主**（`pending_confirm` / `delivered` / `confirmed` 均算），**不必等车主点确认**，该步及之前各步一律只读可看、不可改。发出之前，可以退回上一步修改。  
   - 接车发出 → 接车冻；在检测中不能改接车。  
   - 检测报告发出 → 检测+接车冻；在报价中不能改检测/接车。  
   - 报价发出 → 报价+更早冻；在施工中不能改报价及更早。  
   - **交车报告发出** → 施工及更早全部冻。交车发出前，仍可从交车退回施工补图/说明，也可开补充报价。  
3. **补充报价**：施工中发现未报价项可新增补充报价 → 待车主确认或商家代确认 → **回到施工**继续。补充单发出后该张补充单本身也冻（同「发出即冻」）。

### 3.2 冻结与完成的区别

| 概念 | 含义 |
| --- | --- |
| 发出即冻 | 商家不能再改这一步（及更早）的内容 |
| 步完成 / 解锁下一步 | 接车完成进检测；检测报告发出进报价；**报价须确认**才进施工；施工完成进交车；交车发出等车主确认 |
