## 2. 一句话

> 微信群聊 → 脱敏 → 大模型理解整合 → 人工确认 → 生成符合《07》的公开案例。
> **商家零额外填写**：师傅本来就在群里说话，说话即记录。

---

## 3. 它解决什么，不解决什么

### 3.1 真问题不是"字段太多"，是"谁录入"

小程序那套（10 类目 / 每类目 9–29 项 / 四阶段 / 施工清单 / 删除两步 / 完工关卡）本质是**门店过程管理工具**，要求商家**主动录入**。微信群方案的价值不在字段更少，而在**把"主动录入"变成"被动沉淀"**。

| | 小程序采集 | 微信群归档 |
| --- | --- | --- |
| 商家动作 | 主动：进阶段、点项、挂图、点结论 | **零**（本来就在说话） |
| 学习成本 | 需要培训四阶段与施工清单 | 无 |
| 信息完整度 | 高（如果商家配合） | 中（取决于群里说了多少） |
| 定位 | **主路径** | **存量补救 / 不配合门店的兜底** |

### 3.2 不解决什么

- **不替代**小程序采集主路径；
- **不接管**门店施工过程管理（不做施工清单、不做完工关卡、不做跟进备忘）；
- **不追求**填满 `17` 的全部检查项。

---

## 4. 为什么"信息不全"不是障碍

现有规范已为字段缺失留好降级路径：

**`07` §7.3 字段缺失处理**

| 缺失字段 | 处理方式 |
| --- | --- |
| 车型缺失 | 使用「该车辆」 |
| 里程缺失 | 不展示里程句子 |
| 检查结果缺失 | 使用「门店根据车辆实际情况进行了检查」 |
| 维修方案缺失 | 使用模板默认说明 |
| 图片节点缺失 | **不生成该节点段落** |

**`17` §2.4 车主侧阅读**：清单项**仅展示有真实证据的项**；无图无说明的项**不出现**。

**结论**：流程框架可以保留，**填不满不阻断**——空章不展示，缺项走降级话术。

## 5. 输入限制与如实说明（**必须在工具界面明示，不能只写手册**）

电脑微信「多选 → 复制 → 粘贴」能拿到的只是**纯文本**。以下是硬限制：

| 内容 | 能否拿到 | 现实 | 处理方式 |
| --- | --- | --- | --- |
| 文字消息 | ✅ | 直接可用 | 直接解析 |
| **图片** | ❌ | 只有 `[图片]` 占位符，**图片文件不进剪贴板** | **须单独导出**（见 §5.1） |
| **语音** | ❌ | 只有 `[语音]` 占位符，**不复制文字** | **手机长按语音 → 转文字 → 复制**，再贴进来 |
| 视频/小视频 | ❌ | 占位符 | 同图片，单独导出 |
| 发言人昵称 | ✅ | 含隐私 | **必须脱敏** |
| 时间戳 | ⚠️ | 默认不含，部分版本有 | 有则用，无则不显示 |

> **D3 补充**：语音这条尤其要在工具界面上说清楚——用户以为粘贴了就有，结果语音内容整段缺失，会直接不信任这个工具。**明示优于兜底。**

### 5.1 图片是命门，必须给明确路径

`17` 各项几乎都要求挂图，`07` §7.3 又规定「图片节点缺失 → 不生成该节点段落」。**图片拿不到，案例证据链就断了，真实性门禁（≥60）可能过不了。**

三条取图路径（沿用 `scripts/geo-case-archive/微信群归档操作手册.md`）：

| 路径 | 谁操作 | 说明 |
| --- | --- | --- |
| **B. 截图投递** | 师傅（手机，10 秒） | 保底。发到「盈简归档号」 |
| **C. 逐条转发** | 师傅（手机，20 秒） | 含原图。长按 → 多选 → 逐条转发 |
| **电脑另存** | 盈简（上门/远程） | 上门时直接从电脑微信另存，质量最好 |

**禁用「合并转发」**——生成折叠卡片，内容取不出来。
图片命名：`日期_车型_症状.jpg` / `日期_车型_配件.jpg` / `日期_车型_完工.jpg`。

## 6. 处理流程

```text
① 粘贴群聊文本（含 [图片] / [语音] 占位）
        ↓
② 本地脱敏：手机号 / 车牌 / 姓名 / VIN / 住址 → 占位符
        ↓
③ 大模型理解整合（不是规则匹配）
   - 输入：脱敏后的群聊全文 + 参与人 + 图片计数
   - 输出：事实层（车型/症状/检查发现/方案/过程/完工/工期）
           过程层（3–5 个关键节点）
           存疑项（不确定、需人工确认的）
        ↓
④ 人工确认：增删改，标「不确定」的必须过一道
        ↓
⑤ 按 07 生成案例要素：标题 / 摘要 / 正文九段 / 图说 / 本单问答
        ↓
⑥ 图片单独关联（人工挂到对应节点）+ 图片脱敏
```

### 6.1 为什么交给大模型而不是规则（D3）

真实群聊**没有范本**：技师有时发「图 + 说明」，有时只有一句话，有时语音转文字后断断续续；参与人可能是车主 + 两三个技师；确认过程可能横跨几天。

规则匹配（`17` itemKey 关键词表）必然大量漏判误判。**故：用 `17` 的检查项清单作为提示词的"事实清单"喂给模型，让它自己判断这段话里有哪些事实**，而不是让代码去正则匹配。

### 6.2 大模型提示词要点

- 明确「群聊形态不定，可能只有文字没有图、可能含语音转文字、可能有多个技师」；
- 要求**只提取群聊里真实出现的事实**，未提及的一律留空，**禁止用汽修常识补全**（对应 `07` §1.3）；
- 金额**提取但标记不公开**（§10.1）；
- 输出**存疑项**清单，交人工确认——模型不确定时必须说不确定。

## 7. 数据契约

### 7.1 输出：三层

| 层 | 内容 | 给谁 |
| --- | --- | --- |
| **事实层** | 车型 / 症状场景 / 检查发现 / 方案 / 过程 / 完工 / 照片 | 生成案例正文（AI + 车主） |
| **过程层** | 关键节点时间线 3–5 个：到店检测 → 发现 → 方案沟通 → 车主确认 → 完工 | 只给车主（信任证据） |
| **证据层** | 原始群聊全文（已脱敏）+ 参与人 + 消息数 + 图片数 | 不发布，被质疑时自证 |

### 7.2 输出对齐 `07` 案例要素（D1）

1. 标题（§5） 2. 摘要（§6） 3. 正文九段（§7.1） 4. 图片说明（§9） 5. 本单问答（§1.3）

`17` 的检查项清单**降级为事实提取的参考词表**，不作为必须填满的目标结构。

## 8. 底盘异响（`chassis_noise`）17 项 · 群聊可提取性

> 依据 `17` §5.10。**可提取性为模拟推估，待真实群聊校准。**

| itemKey | 检查项 | 群聊里通常怎么出现 | 可提取性 |
| --- | --- | --- | --- |
| `complaint` | 异响场景 | "过减速带响""转弯咯噔" | ✅ 明确 |
| `bushing_closeup` | 胶套/球头近景 | "胶套裂了" + 图 | ✅ 明确 |
| `sway_bar_links` | 稳定杆连杆/胶套 | "小吊杆球头松了" | ✅ 明确 |
| `repair_path` | 处理路径 | "换小吊杆还是换摆臂总成" + 理由 | ✅ 明确 |
| `old_parts` | 旧件留影 | "旧的拆下来了" + 图 | ✅ 明确 |
| `road_test_after` | 完工路试 | "路试过减速带不响了" | ✅ 明确 |
| `alignment_advice` | 换件后定位 | "顺便做个定位" | ✅ 明确 |
| `press_torque` | 压装/力矩 | "力矩打到标准" | ⚠️ 常省略 |
| `exclude_list` | 已排除项 | "摆臂还能用，不用换" | ⚠️ 隐含，需推断 |
| `road_test_before` | 试车复现 | 客户描述即复现 | ⚠️ 弱 |
| `pry_play_check` | 撬动/旷量检查 | "举起来看了"（不说撬） | ⚠️ 弱 |
| `parts_used` | 配件信息 | 少说品牌，多说"原厂/副厂" | ⚠️ 弱 |
| `odo` | 里程表 | 群里基本不说 | ❌ 缺失 |
| `walkaround` | 环车预检 | 群里基本不说 | ❌ 缺失 |
| `wheel_bearing` | 轮毂轴承 | 没坏就不提 | ❌ 缺失 |
| `shock_strust` | 减震器/顶胶 | 没坏就不提 | ❌ 缺失 |
| `handover_note` | 交车说明 | 少说 | ❌ 缺失 |

**预估**：明确 ✅ 7 项 + 可推断 ⚠️ 4 项 = **11 项**；缺失 6 项走 `07` §7.3 降级。

> **缺失 ≠ 没做**：`wheel_bearing`/`shock_strust` 没提，通常是"检查了没问题"。但按 `07` §1.3「不能手填相册里没有的结论」，**不许反推成"轮毂轴承正常"写进案例**。无证即不写。

## 10. 合规红线

### 10.1 公域藏价（`07` §4.3）

群聊里**几乎必然出现金额**。规则：

- **可提取**（用于判断方案与内档），**禁止写入公开案例**；
- 公开段落写"价格需根据检测结果确认"；
- 社交媒体长文 / 朋友圈同样不写金额。

> 这是群聊方案相对手填的**优势**：金额在群里有据可查，只是不对外展示。

### 10.2 不许编造（`07` §1.3）

> 不能加新图、不能手填相册里没有的结论。

群聊来源是**最硬的证据链**，天然满足 `07` §1.3 的"真实性 ≥60"门禁。但**群里没说的一律不写**，不许用常识补全。

### 10.3 脱敏分两路

| 对象 | 做法 | 现状 |
| --- | --- | --- |
| **文本** | 手机号 / 车牌 / 姓名 / VIN / 住址 → 占位符，**在送大模型之前完成** | **需新建**（简单规则） |
| **图片** | 车牌、人脸、VIN 打码 | **已有**：`backend/src/services/desensitize.service.js` → `runAutoMask`，复用 |

> 顺序不能反：**先脱敏，再送大模型**。客户隐私不得出本机送到外部 API。

### 10.4 信源标识（D2）

```text
门店发布 · 已脱敏 · 已审核
```

### 10.5 隐私

群聊昵称、头像、车牌、手机号、VIN 一律脱敏；照片按 `05_图片视频上传规范.md`、`06_自动脱敏规则.md` 处理。

## 11. 不做的事

| 不做 | 原因 |
| --- | --- |
| 输出 `checklistJson` 全套结构 | 等于把过程管理复杂度搬回来（D1） |
| 用规则/正则去匹配群聊提取字段 | 群聊无范本，规则必然大量误判（D3） |
| 追求填满 17 项 | `07` §7.3 + `17` §2.4 已允许缺失与空章不展示 |
| 自动化插件 / 群机器人 | 封号风险，且把客户群置于风险中 |
| 用「合并转发」取内容 | 折叠卡片取不出文本 |
| 在公开案例写金额 | `07` §4.3 公域藏价 |
| 按常识补全未提及的检查项 | `07` §1.3 不许编造 |
| 把未脱敏文本送外部大模型 | §10.3 先脱敏再送 |
| 现在接入小程序 | 小程序冻结新功能；先按"将来要接入"设计数据结构 |

### 13.2 三处工程决定

| 决定 | 理由 |
| --- | --- |
| **脱敏做两遍**（页面一遍，接口再兜一遍） | 页面上人工改过发言人和内容，可能把隐私改回来；模型之前的那道闸必须在服务端 |
| **昵称换成「发言人A/B/C」而不是直接抹掉** | 模型要靠同一个发言人前后说了什么推断谁是技师谁是车主；全抹成 `[称呼]` 就把对话结构毁了。真名一个字不留（07 §4.1） |
| **生成后再扫一道风控，只报警不自动改** | 模型嘴上答应不写金额，手上还是会写。改文案是人的决定，工具不能偷偷动（07 §17） |

### 13.3 待真实群聊校准的三件事

1. §8 的可提取性评估（现在 11/17 是模拟推估）；
2. 提取提示词里「哪些话算证据、哪些算推断」的分寸（直接决定存疑项数量）；
3. 中文数字金额的风控正则够不够严（群里说「八百六」比说「860」更常见，已加中文数字规则，但难免有误伤）。
