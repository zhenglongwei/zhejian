## 1. 目标

一次服务 = 一条 **按时间排序的节点链**。节点分两类：

| 类型 | 作用 |
| --- | --- |
| **拍照 / 过程节点** | 收过程照片，并在本步写齐下游单据所需正文（主诉、发现项、质保等） |
| **单据节点** | 承载面向车主的单据；按门禁通知或确认 |

商家编辑页 = **单页竖向时间线**（`flow-stepper`）：已完成折叠只读、当前步展开内嵌编辑、未解锁不展示。  
各步标题带本册序号（如「第1步 · 接车」）；**不**在顶部展示「第 n / 总步数」（总步数随增项变化，易误解为固定总长）。**不**在步名旁贴「拍照 / 单据」标签（工单对车主是单据、对店员仍是连拍，标签会打架）。未解锁步直接不渲染，当前卡下**不**写「完成当前步骤后将自动出现下一步」。

**原则**

- **内容前移**：正文在上游过程步填写并自动保存  
- **逐步解锁**：不是一屏摊齐  
- **报告 + 方案合发**：检测证据与报价对车主一次可见；车主只确认方案  
- **用户可见文案 ≠ 产品说明**（设计体系 §2.4.1）  
- **私密报价 ≠ 公域藏价**：方案确认写真实金额；公域案例仍遵价格合规

## 2. 标准节点链（无增项 · 7 步 · flowVersion 6）

```
接车 → 检测 → 检测报告 → 方案确认 → 工单 → 完工照 → 完工确认
```

| sort | kind | 显示名 | nodeCategory | 车主侧（见 `23` §5：单据链，不镜像拍照步） |
| ---: | --- | --- | --- | --- |
| 0 | `intake` | 接车 | photo | 不单独成车主节点 |
| 1 | `inspection` | 检测 | photo | 不单独成车主节点 |
| 2 | `inspection_report` | 检测报告 | document | **与方案同次通知后可阅**（不确认） |
| 3 | `quote_confirm` | 方案确认 | document | **需确认**（真实报价） |
| 4 | `work` | 工单 | document | **只读展示**（不确认） |
| 5 | `delivery_photos` | 完工照 | photo | 不单独成车主节点；交车照进完工确认 |
| 6 | `repair_report` | 完工确认 | document | **需确认** |

**车主时间线** ≠ 上表逐步镜像：车主只见单据链（检测报告 → 方案确认 → 工单 → 完工确认），整链灰显未到步；触达靠线下或分享，**不**依赖相册照片更新订阅（`23` §5.4–5.6）。

> **2026-09-30 · 接车与检测拆分**
> - 「接车与检测」拆成**两个节点**：`intake`「接车」与 `inspection`「检测」；标准链 6 步 → 7 步，`flowVersion` 5 → 6。
> - **接车＝初始状态留证**：**问诊登记** + 连拍进场照（含里程表，可与油量同框）→ 点 **生成接车结果** 出 **接车结果**（读数核验 + 按类目摊图）。**品牌 / 车系 / 年款在新建相册页写好**，进度页顶栏服务名旁边展示，**不进接车正文**。「AI意见」用这份车型。**不做故障判定**、页面**不**贴「正常 / 有破损」。检测步可点选接车已拍外观图，不强制重拍。
> - **检测＝细查**：部位级 `findings`（四档检查结果 + 检查发现），结论进检测报告。
> - 检测报告的**主诉取接车节点**、**发现项取检测节点**（跨节点合成）。
> - legacy 映射恢复历史口径：接车 → `stage_1`，检测 → `stage_2`。
> - **存量 v5 相册不动**：`intake_inspection` 合并节点读侧继续兼容，仅**新建**相册走 7 步。

> **2026-09-28 · 工单语义重构**
> - **废止** `work_order` 节点：工单**不再**是由报价派生的项目清单。
> - 工单 = **如实记录施工过程产生的单据**，由原「施工」节点（`work`）改名而来，性质从过程记录升为单据；标准链 7 步 → 6 步。
> - 工单 = **已确认方案的实现留证**。进入本步时按确认方案行摊开项目，一项引用该行 `quoteLineId`（改名不换身份）。店员按行传图、写一句说明，**不识图归组**。方案外的做成新增项（无 `quoteLineId`），走施工中新发现通知车主。存量无引用的项打开时补一次身份，不按下标重对。
> - 车主时间线纳入工单（**只读、不需确认**），与检测、方案、完工并列为 4 步。
> - 完工报告的施工项与合计**以工单为准**，汇总函数 `collectAllWorkOrderItems`（见 §4.4、§6.6）。

内部 `kind` 仍可用 `quote_confirm` / `repair_report`；产品文案分别为「方案确认」「完工确认」。

### 商家「核对报告与方案」（合一步编辑）

检测确认后，时间线当前步为 **检测报告**，但页面为 **一屏**：

1. **上半**：检测报告（主诉 / 发现项）— 可微调  
2. **下半**：方案项目（按 §4.2.1 出可改草稿；**金额手填**；商家已写过的行不覆盖）  
3. **主按钮「通知车主」**：一次写入  
   - 检测报告 → `delivered`（完成）  
   - 方案确认 → `pending_confirm`（待车主确认）  

**废止**独立「送达车主」（仅报告）按钮。车主在同一次通知后同时看到报告与方案；**仅方案需确认**。

通知后：报告折叠为已完成；当前步变为方案确认（等待确认 / 代确认）。

### 渐进展示

- 仅展示：已完成（一行，可点开只读）+ 当前步（展开）。  
- 解锁：上一步完成（过程 `completed` / 报告+方案已通知 / 方案 `confirmed` / 工单完成等）→ 下一步 `in_progress`。  
- 已完成不可改；修订 = 新节点（二期）。

### 过程步草稿（`photoDraft`）

| 过程步 | 本步须写清 |
| --- | --- |
| `intake` | **接车＝初始状态留证**。页序：**问诊登记** → **AI意见**（自愿）→ **接车照片**（提示把里程表拍进去）。品牌车型已在新建页。**无**独立里程框、**无**拍前环车勾选。点 **生成接车结果** 后出接车结果：里程 / 油量等读数高亮请店员核对；其余按漆面、玻璃、轮胎、灯光、随车物品摊图。页面不写「正常 / 有破损」。照片**不**自动变成检测项、**不**进方案 |
| `inspection` | **检测＝故障与外观细查**。页头可留一句该类基础查什么。区内：**加号 + 从图库选择**，不要再套「检测照片」标题。连拍（或从图库选）进未归组，**传完自动整理**成检测项。某一项里的加号只给该项补图、不识图。列表底下再留一个加号。**不**出现「加一项 / 整理 / 重新整理 / 补拍」并列按钮。未归组剩图才露出 **并入 / 新开 / 删除**（上图、下三钮）。页脚主按钮 **确认并继续**。不拆成报价行。主诉取接车节点 |
| `work` | **工单＝按已确认方案留证**。进入本步时按方案行摊开项目（行名即方案原名，不在工单改）。每一行：**传图 + 一句说明**。页头一句「新旧配件、关键工序」。可从图库勾到某一行。连拍若仍进未归组，只允许 **并入某行 / 新开（报价没有） / 删除**，**不识图**。方案外走「施工中新发现」。页脚 **确认并继续**。旁路见 §3 |
| `delivery_photos` | **交车证据选用**：从本单工单图**引用勾选**；**整车外观必选**（可从工单图选，没有则补拍 1 张）。**不**做按部位分类、**不**写检查发现。质保两行：期限（必填）/ 注意事项（选填） |

确认过程步：缺必填硬拦截。上传与改文自动落库。

### 上传后归组（2026-10-03 · 2026-10-03 补拍改版）

接车、检测：**连拍后自动成项**（接车仍点 **生成接车结果**，因要核对读数）。**工单不识图、不自动成项**，按已确认方案行传图。检测**不**并排「整理 / 重新整理 / 补拍」。检测项列表下留文字链 **加一项**（空项手填，不识图）。拍照加号传到未归组：检测自动整理；工单只并入已有行。界面除按钮「AI意见」外不写「大模型 / 自动分析」。

| 时机 | 检测 | 工单 | 接车 |
| --- | --- | --- | --- |
| 传到未归组 | **传完自动整理** | 不整理；并入已摊开的方案行或新开 | 照片下方 **生成接车结果** |
| 点某一项里的加号 | 只挂到该项，不识图 | 只挂到该行，不识图 | — |
| 没有未归组图 | 不露整理类按钮 | — | — |

**单张 vs 批量**：未归组用同一组件（`flow-unmatched-photos`），每张上图、下三钮 **并入 / 新开 / 删除**，店员指定，不识图。**检测**传到未归组后自动整理才识图成项。**工单**不整理。接车：并入已有接车结果类目，新开选尚未摊开的类目。

**手工兜底**：按流程打码、识图仍没写成项时，未归组图留在页上，每张可 **新开** 再填项目 / 用料 / 说明（检测则填部位 / 检查发现）；已有项时才露 **并入**。不另开「手工上传」入口，界面不写失败原因或「自动 / 模型」。

识图时系统给每张图内部编号，只用来把图放进对应项，**不用文件名找回图片**。写给店员和车主的说明（观察、检查发现、用料、新发现）按**部位和看见的状态**写，**禁止**写「图1、图2、图4」。屏上几张图和内部编号对不上，用户对号会错。没有写进任何项的图留在未归组，三项操作做成按钮。禁止按顺序把剩图塞进项。没有图的组不生成空项。

**何时识图**：传到未归组并自动整理时，以及接车点「生成接车结果」。点某一项里的加号、或点「并入 / 新开」：**不识图**。同一张图识过就缓存，不重跑。**第一次识图要把看见的读数、损伤、部位写全**，供后面报价用。发出前核对：**只把未经整理识过的图送给模型**（项内直传的图会在这里补看）；已识之图只用缓存观察当文字事实，不再附图。

**后一步要带上前面的字，不再看前面的图**（2026-10-08）：检测归组、报价意见、交车对账只带已写成的接车/检测/方案文字，**不再把前序图送第二遍**。工单不识图。本步新图仍只打码一次。

**传图后的顺序（必须做完）**：照片先落库（上传成功）。然后 **先打码、再识图、再成项**。页面保持「归组中」，等到这两步做完再出项。只用打码图识图，不把原图送出去。打码没有「必须几秒完成」；整理一直等到**这一批新图**打码好再识图，**不要等整本相册重打**。查打码只看这一批有没有成功标识，禁止为了刷新整本名单、扫假打码而挡住归组。保存后整本名单在后台补，不挡本步。**每张图只打码一次、只识一次**：打码成功、需人工、失败都算打过，留下标识后任何步骤都不再打。归组只等**这一批**打到终态：打成的用打码图识图成项；打不成的留未归组手工处理，**不得**为其中一张把整批卡住反复重打。完工照补拍在本步落库时打码，不拖到预览。案例预览只展示已打码图，预览失败也不重打。上传失败只说传文件失败，不得把归组等待说成网络/上传失败。整批都打不成时才整步走手工兜底。

**有项之后的版式（检测）**：主体是项列表；列表下文字链 **加一项**；再往下拍照加号（传到未归组并整理）。归组过程中不展示未归组图，只显示「归组中」。完成后写出归到了哪些项；还有剩图再给手工操作。页脚 **确认并继续**。

**工单版式**：主体是已确认方案摊开的行（进步时生成，一项一个 `id`，引用 `quoteLineId`）。每行自己传图、写说明。未归组只 **并入已有行 / 新开 / 删除**，不整理。主按钮上方文字链「施工中新发现」。新增项警示描边 +「报价没有这项 / 去通知车主」。`outsideQuote` 跟项 id 落库。

**工单 · 与方案对齐**：不靠识图猜。进步时方案有几行就摊几项，名称抄方案原名，身份是工单项 `id` + `quoteLineId`。删中间一项、改说明、换图，不得串到别的方案行。新开的项没有 `quoteLineId`。

**检测/工单折叠卡**与车主检测项同构：标题 → 三列方图 → 说明（组件 `flow-finding-card`），不要左字右图。

**防跳过**：未归组图还在时不让确认，拦截「先处理未归组的图」。还没有任何项时不显示确认；有项之后显示确认。加号必须居中、够大。

**已自动保存**：改字、删项先记在**本机**，不写服务器、不删对象存储里的文件。传到未归组后的**自动整理一旦成项，立刻写入本步草稿**（不必等确认并继续）；再进工单/检测仍是项，不得把已归组图退回未归组。点 **确认并继续** 才完成本步。项目删光就是空列表，**不得**用图库里还留着的旧图把项拼回来。清手机缓存会丢掉尚未写进草稿的改动。提示约 2 秒后消失。

**删项 / 删未归组图**：该项的文字和挂图从本步草稿拿掉（文字仍先记本机）。照片**不从服务器删除**，马上从这一步卸下，改挂到**本单图库**。之后同一张图再要用，从图库勾选，不必重新上传。确认并继续再把「项已拿掉」写进服务器草稿。

| 步骤 | 成项做什么 | 不做 |
| --- | --- | --- |
| 接车 | 按类目归组；抽出里程 / 油量等读数供核对 | 不在页面写正常/破损；不生成「需处理」；识图全文按图缓存 |
| 检测 | 按**检查点 / 部位**归组。页上提示该类基础要查什么。传到未归组后自动整理 | 不按一张图一项；不生成报价行；不自动把接车图变成检测项；不默认摊开接车缩略图；项内补图不识图 |
| 工单 | 按确认方案行摊开；图挂在该行身份上 | 不识图归组；不把方案外的图自动算已报价；不写检查结果；不改已经确认的检测和报价正文；不自动插入增项单 |
| 完工照 | **不成项**。从工单图勾外观，缺则补拍 | 不按部位分类、不写检查发现 |

成项是帮店员填本步草稿；**发给车主前的核对**仍按确认前检查另走一次，两者不抢着改同一句。未归组的图可并入、新开或删除。

文案：店员侧短、像工位上说话；车主侧用能看懂的说法，不把「需处理」当行名。商家接车写 **问诊登记**，车主/检测报告仍可称 **进店主诉**（同一字段）。**品牌车型在新建页填写**；车主侧仍是品牌 / 车系 / 年款。

### 接车页 · 接车结果 · 按图只识一次（2026-10-03）

店员真实顺序：建档时先核对车型，进接车再问清来修什么，然后连拍进场（仪表与油量经常同一张）。

| 区 | 规则 |
| --- | --- |
| 页序 | **问诊登记** → **AI意见**（自愿）→ **接车照片**（提示把里程表拍进去）→ **生成接车结果** → **接车结果**。品牌/车系/年款在新建页，进度顶栏服务名旁展示 |
| 取消 | 独立「当前里程」拍摄框；拍前环车勾选；清单里的「仪表（里程）」单独项 |
| 接车结果 | **里程、油量等读数高亮**，店员核对后可改。其余按 **漆面、玻璃、轮胎、灯光、随车物品** 摊图。**不**在接车页输出正常 / 有破损 |
| 识图缓存 | **检测**：传到未归组后自动整理才识图。接车点「生成接车结果」。工单项内补图、并入不识图。识图全文按 **同一张图** 缓存。文件未变则复用，不重跑。 |
| 检测引用 | **不**自动把接车图变成检测项。检测页：首次连拍在上，「**从图库选择**」在下；有项之后改为 **补拍** 一行。默认不摊开接车缩略图。钣喷类目提示进场外观已在图库。 |
| 本单图库 | **这本相册已经传到服务器的图**，不靠手机本地缓存。清缓存后仍能打开。不跨单、不跨店。含：还挂在某一步上的图，以及从项上卸下、只留在库里的图。卸下后条目标「图库」。检测、工单都可勾进本次；按钮写 **选用**，已在本次的写 **已选**。界面不写「大模型 / 自动分析」。图库不是流程步，车主时间线与商家进度里都不出现。 |

接车类目 id 见 `INTAKE_RECORD_CATEGORIES`（`odometer` / `fuel` / `paint` / `glass` / `tire` / `light` / `belongings`）。存量 `WALKAROUND_PARTS` 勾选只读兼容，新单不再作为拍前清单。

### AI意见（2026-10-10 定稿）

意见是给人读的对照（故障怎么看、建议查哪、报价怎么讲、车主可能问、交车对账）。**作业表钉在主页面**（检测项、方案行、工单按方案摊开的行），和意见不是一回事：模型写出的格式化表格写进主表，店员接着改。意见本身做成**可开关的阅读页**：点「AI意见」展开，再点「收起」或遮罩关掉，不占死主流程。版式：分区标题 + 条目标题/正文。除交车通知前强制跑（跑完自动展开一次，仍可收起）以外，店员自己点。发给车主的仍是门店确认件，界面不写模型名。

真源提纲见 [`28_`](./28_节点AI检查_用户关心点与开发计划.md)。

| 步 | 何时出 | 出什么 | 强制？ |
| --- | --- | --- | --- |
| 接车 | 主诉非空即可点；不必先传留证照。车型取新建页已写入的品牌/车系/年款 | 阅读层顺序：**建议进一步了解**（可勾选项写入问诊）→ **初步诊断** → **先做环车检查，避免后续纠纷**（仅进场留证，不写举升检测）→ **检测顺序**（按优先级）。各块不复述。检查点带稳定 `id` | 否 |
| 检测 | 连拍**归组完成后立刻对照**，不再跑模型 | 用已有接车意见的检查点对照本次发现项：意见里有、这次没对上的，贴在项下或列表下，不强制补 | — |
| 报价 | 店员点「AI意见」 | 建议项目与施工方案（金额空）、市场参考价、可能漏了、车主可能问。写入可改的方案表。类目边界见 §4.2.1 | 否 |
| 工单 | 不出意见 | 按确认方案行传图 | — |
| 交车通知前 | **系统强制跑**，店员须看到结果再通知 | 整单是否说得通。接车/检测/报价**只当上下文，不提请改确认件**。只对工单、完工选用、交车说明提**错项、漏项**。**不润色原文** | 是 |

**不做**：报价发出前再换模型复查；用模型改店员已写的句子；把漏项自动加进报价；工单识图猜属于哪一行；公开案例那一步再改车主已经看过的交车报告。

**对象**

- **接车意见**：挂在接车节点。一份意见；检查点 `{ id, partName, why, sortOrder }`，身份是 `id`。追问可带选项，勾选后写入问诊登记。环车留证与举升检测分两块，禁止混写。店员再点可按主诉指纹更新，不另生平行份。
- **检测对照**：归组项身份仍是发现项 `id`。对照结果是「检查点 id → 是否对上某发现项」，贴建议，不改发现项。
- **报价意见**：建议行写入方案 `lines[]`（行 `id`）；话术与参考价住在方案节点店内稿，按行 `id` 贴，不按下标。
- **工单项**：见 §4.3。实现行引用 `quoteLineId`；图跟工单项 `id`。
- **交车意见**：只指向工单项 / 交车字段，可用「应用」写空栏或补图，**已有字不覆盖**。

| 规则 | 口径 |
| --- | --- |
| **硬拦 vs 建议** | 缺必填仍硬拦。意见不挡「确认并继续」。交车强制意见未出完前不发通知。建议贴在对应项下：文案旁「应用」只改空栏；已有字不覆盖。不弹层、不批量替换 |
| **必须先看到再决定** | **仅交车通知前**：意见未出时不发。等待时主按钮收起，一行「正在出意见」。关掉小程序后继续；再打开仍停在本步 |
| **先打码再识图** | 只用打码图问模型；失败不把原图送出去。检测整理等到本批打码再成项。每张图只打一次、只识一次 |
| **不改什么** | 不改金额、不编隐藏件、不建议合并增项轮次；已发给车主的确认件不经店员点不改写 |
| **能力开关** | 总闸关闭或未开通：不出现「AI意见」，交车直接按必填通知。前期全员免费（见 `28_` §4.4） |

界面：短句、商家口吻。不出现「提示词 / 自动优化 / 大模型 / 套餐」。按钮允许写「AI意见」。意见用阅读层，不把长文塞进主表下方。

**施工多图 / 交车选用（2026-09-09）**

- 工单按「做成的项」留证：同一项可多张（新旧配件、包装、关键工序等）。检测同一部位的补拍也并入该项；只有对不上时才新开一项。  
- **不**再维护与施工平行的第二套「完工相册」；交车图 = 对工单图（及少量补拍）的**引用**，档案不因勾选而复制文件。  
- **整车外观必选**：工单图默认是旧件/新件，通常没有车身全貌；无外观时在完工照补拍（或从工单图中指定一张为外观），不默认整本重拍。  
- 旧件特写默认不进车主交车区，除非商家勾为交车图。

## 3. 增项（一期）

施工中入口：工单页脚主按钮上方的文字链 **施工中新发现**，以及工单行上 **去通知车主**（项已标报价没有这项时）。勿写「添加方案」，勿用通栏大按钮。点一次即可；**本张工单里所有「报价没有这项」的项进同一张增项单**，不要一项开一张。已有未发出或待确认的新发现时，再点只回到这一页，不另开一张；若该页还是空行，则把工单里尚未带入的项补进去。  
公网档案**保留**由此产生的多段方案 / 工单 / 施工，不合并、不按主项裁；第二轮方案标题用「施工中新发现」（见 `15_` §7.9）。  

插入一张 **方案确认**（`quote_confirm`，`insertedReason=addon`）。

- **工单里已有新增项**（`outsideQuote`）：把这些项的项目名、用料/说明、照片**带进**增项单。图仍挂在工单行身份上，增项行用 `workFindingId` **引用**同一批图，不另拍、不按下标对。金额仍手填。新发现区用这些图和说明预填并视为已写好，店员补金额后即可通知车主。
- **工单里还没有这类项**（空态点入口）：同一页先写 **新发现**（故障照片 + 看见什么），写好后再填 **项目与费用**。

项目与费用字段与首次报价相同：项目、品牌（选填）、施工方案、金额。车主确认 → **新开工单步**（时间线**另开一张**，与首张工单并列，不合并）→ **继续记录施工**（确认后直达工单步，不必卡在空工单页）→ …  

**单据大标题（商家 + 车主统一）**：**施工中新发现**。时间线段标签可弱标「增项」。  

未发送车主前，方案/增项费用行可 **增删**（至少保留一行空壳便于继续填）。

### 3.1 整张作废（误点入口 / 线下谈妥不做）

- **谁操作**：仅商家。  
- **何时**：增项「施工中新发现」处于未发或等待车主确认；**车主已确认后不可作废**。  
- **未发出（误点）**：直接删掉本张增项及后续未开工单步，**不留时间线记录、不填原因、不通知车主**；当前回到原工单步。  
- **已发送待确认**：作废须 **必填原因**；时间线保留该步，状态「门店已取消」+ 原因（**商家与车主均可见**）；撤掉后续未开工单步；回到原工单步。  
- **车主已确认**：不可作废。  

### 3.2 车主不同意

待确认的方案、施工中新发现、完工确认，车主都可以点 **不同意**。电话联系门店仍保留。

- **施工中新发现**：效果与商家「取消本项」相同（这项不做，回到工单步）。记录为 **车主未同意**，原因记「车主拒绝」，不记成门店取消。车主与门店都看得到。  
- **首次方案、完工确认**：整单不删。单据退回门店可改，状态记 **车主未同意**。门店改完可再发。  

**工单草稿**：打断增项前须落库当前工单草稿；各工单步 `photoDraft.findings` 按 `id` 合并读取，避免项目名丢失。增项单从当前工单里 `outsideQuote` 的项按 **项 id** 带出图文；增项确认后新开的工单步仍由商家继续填，**不**按报价行再派生一套项。  

**工单合并时机**：时间线保持多张工单（如实按事件发生的顺序记录）；**仅完工确认**汇总全部工单项目与金额（`collectAllWorkOrderItems`，取 `work` 节点 `findings`）。  

二期可加独立「增项检测」拍照节点。

```
工单 ⇄ 施工中新发现 → 工单(增项·独立) → … → 完工照 → 完工确认(合并全部工单项)
```

**验收**：改增项相关代码前后，按 [`27_DOC-FLOW增项最小验收清单.md`](./27_DOC-FLOW增项最小验收清单.md) 点测。

## 4. 单据字段表与生成规则（真源）

> 不用大模型。一期规则生成 + 商家微调。

### 4.1 检测报告 `inspection_report`

| 区块 | 字段 | 规则 |
| --- | --- | --- |
| 页头 | 车辆 / `mileageText` / `chiefComplaint` / `reportDate` | 相册车辆档 + 接车步 `photoDraft.mileageKm`（与仪表照同区；识别可填、以手改为准）；**不要**从发现项图注里猜公里数 |
| 发现项 | `findings[]` | **一项一个对象**：`partName`；`images[]`（该部位的照片，可多张）；`result` ∈ {状态良好, 需关注, 需处理, 仅记录}；`advice`。相册里的照片列表由这项生成。提交时直接校验这项，不按照片地址把结果重新配对 |
| 未检 | `disclaimer` | 落库可保留固定套话；**车主端不展示**该长句，发现项列表上方用分区标题「本次检测项目」 |

> **检测 ≠ 方案。** 检测图回答「查了什么、看见什么」；方案回答「准备做什么」。报价表**不是**检测表的投影，也不拿两张表做项目配对。  
> **封闭类目**（小保养 / 大保养 / 电瓶，以及刹车、轮胎、空调的附加项）：草稿来自「这次来做什么」的套餐，检测只决定加不加附加项。状态良好、仅记录、需关注默认不出行。套餐外对不上的发现**不自动进报价**。  
> **开口活**（事故车、底盘异响、通用）：第一张方案是**初步方案**——已写明需处理的可见项 + 一行拆检（写清拆哪）。未拍到的隐藏件只作内部提醒，不进车主要确认的收费行。拆检后新发现走增项，再确认施工范围。  
> 照片只留在检测发现项上。检测结果档**只留在检测报告**，不写进方案/工单行名。金额一律手填。  
> **校验**：部位必填；结果必选四档之一；**需关注 / 需处理** 时检查发现必填；**状态良好** 默认「无需处理」（可改）；**仅记录** 不要求检查发现、不进方案证据池。修/换写在**方案处理建议**里。  
> **一项的边界**：照片、部位、检查结果、检查发现属于同一项。补拍只往 `images[]` 里加，不新开一项，也不换掉原照片。相册节点图片是这项的投影；旧数据里只有散图、没有发现项时，才按图注归到同名部位，归不上才新开一项。施工同样是一项多图，只是没有检查结果和检查发现。  
> **分工**：`chiefComplaint` = 客户进店原因；发现项 = 技师所见（含留证图）；方案行 = **准备做什么**与金额。占位按 `templateId`。  
> **废止商家填写「结论」**：一期不以整单结论栏替代发现项。  
> **与已废止「现象/症状」栏的关系**：检查发现写技师所见，不是把客户口述再抄一遍。

**生成**：检测确认 → 报告完整草稿（主诉取接车节点）。方案空着，等店员点「AI意见」再出建议行（§4.2.1）；未点或未开通：可手填，或回落类目规则草稿。照片不复制到方案行。检测拍照步确认后即固定，**不再回写**；通知车主成功前，报告与方案上的图文仍可改（改在本页草稿，不改已确认的检测步）。  
**门禁（商家）**：在「核对报告与方案」一屏补齐项目名与金额后 **通知车主** → 报告 `delivered` + 方案 `pending_confirm`。**通知成功后本页不可再改**（车主已能看见）。  
**车主**：报告可阅、**不确认**；与方案同次出现。

### 4.2 方案确认 `quote_confirm`

| 字段 | 说明 |
| --- | --- |
| `lines[]` | `{ name, brand?, amount, note }`；`name`=**要做的事**（如全车补漆）；`brand`=**配件品牌**（选填）；`note`=施工方案（车主侧称处理建议）；`amount` 为 **真实金额（元）**。首张方案不挂检测图。`evidenceUrl` / `evidenceUrls` 仅增项故障图沿用 |
| `confirmCopy` | **固定协议文案**（商家不可改）。封闭类：本人同意按上述项目施工，费用以本单为准。开口活：本人同意按上述项目施工（含约定拆检）。拆检后如有增减，须再确认。费用以各次确认单为准。 |
| `evidenceRef` | 关联检测报告节点 id（首张方案）；增项以行内证据图为准 |

商家改项目名和金额；可删可加。存量已写过的行不覆盖。  
**门禁**：≥1 行且每行 `amount` 为有效数字；**增项**另要求每行有故障图；与报告一并通知 / 增项发送后待确认；车主确认或代确认 → **解锁工单步**（进入工单时按确认方案行摊开留证项）。  
**商家编辑**：一行四格——**项目** / **品牌**（选填）/ **施工方案** / **金额**。项目列表下方、合计上方用「新增项目」加行。改完自动保存，不单独「保存草稿」。开口活方案区一行短提示：「拆开后如有增减，再通知车主」。不放检测图。**不展示**确认文案；车主确认页仍称处理建议。

#### 4.2.1 方案草稿（检测完成后、方案仍空时）

金额、品牌一律空。**施工方案不粘贴检查发现原文**。界面不写生成方式。出建议时不再把接车/检测图送第二遍，只用已写成的主诉、发现项、检查结果。

**能力开通时（默认）**：店员点「AI意见」后出建议报价（项目与施工方案、市场参考价、可能漏了、车主可能问）。成交价空着店员填。不预填检测说明。不自动跑，发出前不再换模型复查。

车主发出去的仍是门店确认件。

**类目边界（模型不得越过，失败时规则草稿同此表）**：

| 类目 | 草稿怎么来 | 默认行 |
| --- | --- | --- |
| 小保养 / 大保养 | 套餐主项必须在；附加仅需处理 | 主项「更换机油机滤」；附加：空滤、空调滤等（仅需处理） |
| 电瓶 | 套餐主项 | 「更换电瓶」 |
| 刹车 | 需处理按轴合并 | 前/后片分开；片与盘分开；刹车油另开 |
| 轮胎 | 需处理的胎 | 按条 |
| 空调 | 需处理项 | 滤芯 / 冷媒等各算各的 |
| 钣喷 | 需处理的板件 | 一行一块板，不合成全车喷漆 |
| 事故车 / 底盘异响 / 通用 | 初步方案 | 可见需处理项 + **拆检**（写清拆哪）；未出现的隐藏件不进收费行；事故车不估金额 |

**不出行**：状态良好、仅记录、需关注（默认可手加）、巡检类、套餐外对不上的部位。  
**对象**：建议报价行写入方案 `lines[]`，身份仍是行 `id`（改名不丢）。店员已改过项目名的行不覆盖。  
**拆检后**：走 §3 施工中新发现。

报价「AI意见」一次出齐建议表与话术。漏项只写在意见里，不自动加行。事故车不估金额。

### 4.3 工单 `work`

工单是**已确认方案的实现留证**，不是再诊断，也不是干活录像。进入本步时按确认方案行摊开，商家按行传图、写一句说明。

| 字段 | 说明 |
| --- | --- |
| `findings[]` | 工单项目。一项 = `{ id, quoteLineId?, partName, caption, material?, brand?, qty?, amount?, images[], outsideQuote? }` |
| `quoteLineId` | 实现哪一行已确认方案。方案摊开的项必有；新增项没有 |
| `partName` | 已报价项 = 方案行原名，不在工单改；新增项才手写 |
| `caption` | 施工说明（选填）：图上能见的旧件状态、规格 |
| `material` / `brand` / `qty` / `amount` | **不在工单页填写**。品牌、数量、金额写在方案。存量字段可读，界面不露 |
| `images[]` | 本项证物图（含新旧配件、关键工序等），一项可多图 |

**填写**：折叠卡点标题可展开：**补图 + 说明**。已报价项不改项目名。新增项可改名，项上标 **报价没有这项**，点 **去通知车主**。不自动开增项单。不识图。

**门禁**：≥1 项且每项有 `partName`；每项至少 1 张图。

工单完成时**不**跑意见。对账放到交车通知前的强制「AI意见」。

**多工单并存**：每次增项开一张新工单，在时间线**并列、不合并**，如实按事件发生的顺序记录；仅**完工确认**汇总全部工单项目。

**车主侧**：单据时间线里只读展示（施工项 + 用料 + 图），**不需车主确认**。

### 4.4 完工确认 `repair_report`

| 区块 | 字段 |
| --- | --- |
| 已施工 | 全部工单 `findings`（含增项工单），由 `collectAllWorkOrderItems` 汇总 |
| 合计 | **以工单为准**：工单项目填了金额 → 取工单合计，且**必须与已确认报价一致**（不一致须先走增项确认，否则阻断发出）；工单未填金额 → 回落到已确认报价（含增项）合计 |
| 验证 | `deliveryPhotos[]` |
| 质保 | **期限**（必填、实质内容）+ **注意事项**（选填；范围/除外等合写）；存量 scope/exclusions 读侧拼入注意事项 |
| 确认文案 | **固定协议文案**（商家不可改） |

**生成**：完工照确认后。车主确认或代确认成功后，**自动整单完工**（相册 `completed`）。

## 5. 确认与代确认

**需车主确认**：仅 `quote_confirm`（首张「方案确认」/ 增项「施工中新发现」）、`repair_report`（完工确认）。  

**不需**：`inspection_report`（随方案通知后可阅）、`work`（工单，只读展示）。

**确认文案**：平台固定协议句，写入单据 payload；**商家报价/完工编辑页不展示、不可改**；**车主确认页展示**。

### 商家操作两阶段（方案 / 增项 / 完工）

| 阶段 | 单据状态 | 商家底栏 | 状态文案 |
| --- | --- | --- | --- |
| 编辑 | `draft` | **仅**主按钮「发送车主确认」（发送时保存；**不**单独「保存草稿」） | **不标「草稿」**（摘要可空） |
| 待确认 | `pending_confirm` | 提示「等待车主确认」+ 次按钮「代车主确认」 | 待车主确认 |
| 已确认 | `confirmed` | 无操作 / 只读 | 车主已确认 / 商家代确认 |

**商家代确认**：仅在「待确认」阶段出现，入口为次按钮「代车主确认」。点后先弹窗确认前提——**仅限车主当面、电话或微信已同意，但未在手机确认**；确认后再二选一：**附同意截图（聊天记录即可）** / **不留痕，直接确认**（在确认流程内选传，**不**单独占一行「上传证明」按钮）。

| 状态 | 展示 |
| --- | --- |
| draft | （商家面不展示「草稿」标签） |
| delivered | 已送达（检测报告，随「通知车主」写入） |
| pending_confirm | 待车主确认 |
| confirmed | 车主已确认 / 商家代确认 + 时间；代确认可选证明图 |

### 6.3 发现项 `finding`（一项的边界）

**属于同一发现项的字段必须住在同一个对象里。禁止按数组下标或图片 URL 跨数组配对。**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | **稳定标识**，见下方 id 规则 |
| `partName` | string | 部位 / 施工项目名。**不是身份**，可重名、可改 |
| `images` | array | 该项图片 `{url, imageId}`，最多 6 张；显式 `[]` 表示已删光，不得用 `url` 回填 |
| `url` / `imageId` | string | 首图冗余，供读侧兼容 |
| `result` | string | 检查结果（状态良好 / 需关注 / 需处理） |
| `advice` | string | 检查发现 |
| `quoteLineId` | string | 关联的方案行 / 工单项 `id`（施工项，可空） |

### 6.4 `id` 规则（真源）

1. **新建** finding 必须分配 `id`。
2. **读取**：`normalize*` 保留 `raw.id`；缺失时按下述顺序生成，且生成后**立即持久化**（页面有自动保存，存量数据打开一次即完成迁移）。
   - 首图指纹：`fid_<媒体键>` —— 同一张图多次 normalize 得到同一 id
   - 仍取不到：`fid_i<下标>` —— **仅存量首次迁移命中**
3. `id` 落库后不随顺序调整、改名、换图而变化。删除项后其 `id` 不复用。

### 6.5 配对规则

- **一律按 `id` 配对**。禁止用数组下标、展示顺序、图片 URL 反查，把 `photos[]` 与 `findings[]` 对齐成一条记录。多图挂在 finding 的 `images[]` 上。
- **禁止用 `partName` 当主键**做合并或匹配（部位可重名）。同名不同 `id` 视为两项。
- 工单**实现行**用 `quoteLineId` 引用已确认方案行（2026-10-10）：一对一实现，不是按下标、不是按名称合并。检测发现项与工单仍不配对。新增项（方案外）没有 `quoteLineId`。存量无引用的项打开时补一次 `id`，能对上唯一方案行的才补 `quoteLineId`，对不上保持新增。
- 散图与 finding 的关联只认 `imageId` / `url`。位置兜底仅允许在存量「一图一项」且两侧数量相等时启用一次，生成 `id` 后不再命中。

**存量兼容**：旧形状在 normalize 里只读不写回；新写入必须是本节结构。

### 6.6 工单按确认方案行摊开（2026-10-10）

> 废止「进工单空白、靠识图猜属于哪一行」。工单是方案的实现留证。

1. 进入工单步（尚无 findings）时：按**本段对应的已确认方案**每一行生成一项 `{ id, quoteLineId, partName: 方案行原名, caption: '', images: [] }`。`id` 新建，不复用方案行 id。
2. 项目名已报价项不改；检测结果档不写进工单行名。
3. 图挂在**本项** `images[]`，跟 `id` 走。
4. 方案外新开项：新 `id`，无 `quoteLineId`，`outsideQuote`。
5. 展示顺序：先方案摊开顺序，新增项排在末尾。
6. **不识图**。未归组图由店员并入某 `id`。

**多工单并存**：增项工单与首张工单在时间线**并列、不合并**（§3、§4.3），如实按事件发生的顺序记录；仅**完工确认**汇总全部工单项目（`collectAllWorkOrderItems`，取 `work` 节点的 `findings`）。

**增项流程**（施工中新增项目）——不在施工节点自由添加，回到方案侧闭环：

1. 商家点「施工中新发现」或项上「去通知车主」→ 插入一张 `quote_confirm`（`insertedReason=addon`），带入当前工单全部「报价没有这项」的图文；没有这类项才出空白新发现页
2. 车主确认或商家代确认
3. 自动**新生成一张增项工单**（与首张工单**并列、不合并**），并插入一个新的施工步（带入前序已传 findings）
4. 新施工步按**该轮已确认增项方案**摊开项目（与首张工单同一口径，见 §6.6）；前序已传、尚未挂上方案行的图保留在未归组，由店员并入，不按名称自动归位

## 7. 门禁

- 过程步必填硬拦截（主诉/发现项/质保）。  
- 「通知车主」：报告完整 + 方案金额硬校验。  
- 整单完工：完工确认（车主确认或商家代确认）成功后**自动**将相册标为 `completed`（通知、预脱敏等）；不再要求商家二次点「标记整单完工」。存量若步骤已齐但相册未完工，商家端可保留一次补点入口。
- **案例托管**：相册 `completed` 后，flow 页底栏出现「托管到案例站」；编辑页只读态同入口。主路径为**原始档案托管**（私密 / 公开二选一），废止「本地生成优化案例稿再推送」。公开须隐私校验 → **内容检查（软建议）** → 生成 GEO → 门店确认 GEO 后才上店页（见 `15_` §7.11 · `19_`）。缺里程不拦完工，公开前警告。
