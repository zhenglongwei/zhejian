## 1. 目标

一次服务 = 一条 **按时间排序的节点链**。节点分两类：

| 类型 | 作用 |
| --- | --- |
| **拍照 / 过程节点** | 收过程照片，并在本步写齐下游单据所需正文（主诉、发现项、质保等） |
| **单据节点** | 承载面向车主的单据；按门禁通知或确认 |

商家编辑页 = **单页竖向时间线**（`flow-stepper`）：已完成折叠只读、当前步展开内嵌编辑、未解锁不展示。  
各步标题带本册序号（如「第1步 · 接车」）；**不**在顶部展示「第 n / 总步数」（总步数随增项变化，易误解为固定总长）。

**原则**

- **内容前移**：正文在上游过程步填写并自动保存  
- **逐步解锁**：不是一屏摊齐  
- **报告 + 方案合发**：检测证据与报价对车主一次可见；车主只确认方案  
- **用户可见文案 ≠ 产品说明**（设计体系 §2.4.1）  
- **私密报价 ≠ 公域藏价**：方案确认写真实金额；公域案例仍遵价格合规

## 2. 标准节点链（无增项 · 7 步 · flowVersion 6）

```
接车 → 检测 → 检测报告 → 方案确认 → 工单 → 完工照 → 完工确认
```

| sort | kind | 显示名 | nodeCategory | 车主侧（见 `23` §5：单据链，不镜像拍照步） |
| ---: | --- | --- | --- | --- |
| 0 | `intake` | 接车 | photo | 不单独成车主节点 |
| 1 | `inspection` | 检测 | photo | 不单独成车主节点 |
| 2 | `inspection_report` | 检测报告 | document | **与方案同次通知后可阅**（不确认） |
| 3 | `quote_confirm` | 方案确认 | document | **需确认**（真实报价） |
| 4 | `work` | 工单 | document | **只读展示**（不确认） |
| 5 | `delivery_photos` | 完工照 | photo | 不单独成车主节点；交车照进完工确认 |
| 6 | `repair_report` | 完工确认 | document | **需确认** |

**车主时间线** ≠ 上表逐步镜像：车主只见单据链（检测报告 → 方案确认 → 工单 → 完工确认），整链灰显未到步；触达靠线下或分享，**不**依赖相册照片更新订阅（`23` §5.4–5.6）。

> **2026-09-30 · 接车与检测拆分**
> - 「接车与检测」拆成**两个节点**：`intake`「接车」与 `inspection`「检测」；标准链 6 步 → 7 步，`flowVersion` 5 → 6。
> - **接车＝初始状态留证**：**问诊登记** + **品牌车型** + 连拍进场照（含里程表，可与油量同框）→ 点 **整理** 出 **接车结果**（读数核验 + 按类目摊图）。**不做故障判定**、页面**不**贴「正常 / 有破损」——目的是留证车辆进场时什么样。检测步可点选接车已拍外观图，不强制重拍。
> - **检测＝细查**：部位级 `findings`（四档检查结果 + 检查发现），结论进检测报告。
> - 检测报告的**主诉取接车节点**、**发现项取检测节点**（跨节点合成）。
> - legacy 映射恢复历史口径：接车 → `stage_1`，检测 → `stage_2`。
> - **存量 v5 相册不动**：`intake_inspection` 合并节点读侧继续兼容，仅**新建**相册走 7 步。

> **2026-09-28 · 工单语义重构**
> - **废止** `work_order` 节点：工单**不再**是由报价派生的项目清单。
> - 工单 = **如实记录施工过程产生的单据**，由原「施工」节点（`work`）改名而来，性质从过程记录升为单据；标准链 7 步 → 6 步。
> - 工单项目由商家自由填写，**不要求**与检测发现或报价行勾连（`quoteLineId` 不再作勾连依据，仅存量兼容）。
> - 车主时间线纳入工单（**只读、不需确认**），与检测、方案、完工并列为 4 步。
> - 完工报告的施工项与合计**以工单为准**，汇总函数 `collectAllWorkOrderItems`（见 §4.4、§6.6）。

内部 `kind` 仍可用 `quote_confirm` / `repair_report`；产品文案分别为「方案确认」「完工确认」。

### 商家「核对报告与方案」（合一步编辑）

检测确认后，时间线当前步为 **检测报告**，但页面为 **一屏**：

1. **上半**：检测报告（主诉 / 发现项）— 可微调  
2. **下半**：方案项目（由「需关注 / 需处理」发现项预填**部位名**；**金额手填**）  
3. **主按钮「通知车主」**：一次写入  
   - 检测报告 → `delivered`（完成）  
   - 方案确认 → `pending_confirm`（待车主确认）  

**废止**独立「送达车主」（仅报告）按钮。车主在同一次通知后同时看到报告与方案；**仅方案需确认**。

通知后：报告折叠为已完成；当前步变为方案确认（等待确认 / 代确认）。

### 渐进展示

- 仅展示：已完成（一行，可点开只读）+ 当前步（展开）。  
- 解锁：上一步完成（过程 `completed` / 报告+方案已通知 / 方案 `confirmed` / 工单完成等）→ 下一步 `in_progress`。  
- 已完成不可改；修订 = 新节点（二期）。

### 过程步草稿（`photoDraft`）

| 过程步 | 本步须写清 |
| --- | --- |
| `intake` | **接车＝初始状态留证**。页序：**问诊登记** → **品牌车型** → **接车照片**（提示把里程表拍进去）。**无**独立里程框、**无**拍前环车勾选。点 **整理** 后出接车结果：里程 / 油量等读数高亮请店员核对；其余按漆面、玻璃、轮胎、灯光、随车物品摊图。页面不写「正常 / 有破损」。照片**不**自动变成检测项、**不**进方案 |
| `inspection` | **检测＝故障与外观细查**。加号一次可选多张，图先进**本次照片**，不立刻变成一项。点 **整理** 按部位归组：一项 = 部位 + 多张图 + 检查结果 + 检查发现，店员可改。整理之后补拍：对得上已有部位则并入该项，对不上再新开。任何类目都可以是多个检查点对应一项要做的事，整理只出检查点，不拆成报价行。主诉取接车节点 |
| `work` | **工单＝如实记录施工**。同样先堆图再 **整理**：按「做了哪一项」归组（项目名 + 施工说明 + 多图），**无**检查结果。整理之后补拍并入已有施工项。不改已经固定的检测和报价 |
| `delivery_photos` | **交车证据选用**：从本单工单图**引用勾选**；**整车外观必选**（可从工单图选，没有则补拍 1 张）。**不**做按部位分类、**不**写检查发现。质保两行：期限（必填）/ 注意事项（选填） |

确认过程步：缺必填硬拦截。上传与改文自动落库。

### 上传后整理（2026-10-03）

接车、检测、工单：**先拍进本次照片，再点「整理」** 归组和填说明草稿。连拍是常见情况；整理完毕后发现漏拍，补上的图对得上已有项就并入，对不上才新开一项。**一项必须带图**：对不上文件名时把未用图按顺序挂上，没有图的组不生成空的「待拍照」项。界面不出现「自动分类 / 大模型」等实现话术。界面不写「待整理」。

**防跳过整理**：检测/工单页脚只排 **整理** 与 **确认并继续**（左右并列，避免上下误触）。「从图库选择」保持文字链，放在加号下方。未点过整理时不显示确认；点过整理后确认出现，整理按钮仍保留。若仍有未归组图就去确认，拦截「先点整理」。

**已自动保存**：保存成功后显示约 2 秒即消失；失败提示常驻到下次保存。平时不占一行。

| 步骤 | 整理做什么 | 不做 |
| --- | --- | --- |
| 接车 | 按类目归组；抽出里程 / 油量等读数供核对 | 不在页面写正常/破损；不生成「需处理」；识图全文按图缓存 |
| 检测 | 按**检查点 / 部位**归组。页上提示该类基础要查什么（如油液、故障灯、底盘、刹车、轮胎）。上传在上，「从图库选择」在下 | 不按一张图一项；不生成报价行；不自动把接车图变成检测项；不默认摊开接车缩略图 |
| 工单 | 按**做了哪一项**归组，预填项目名和施工说明 | 不写检查结果；不改已确认的检测和报价 |
| 完工照 | **无「整理」**。从工单图勾外观，缺则补拍 | 不按部位分类、不写检查发现 |

整理是帮店员填本步草稿；**发给车主前的核对**仍按确认前检查另走一次，两者不抢着改同一句。关总闸时仍可手把本次尚未归组的图加到已有项或新开一项。

文案：店员侧短、像工位上说话；车主侧用能看懂的说法，不把「需处理」当行名。商家接车写 **问诊登记**，车主/检测报告仍可称 **进店主诉**（同一字段）。商家接车写 **品牌车型**，车主侧仍是品牌 / 车系 / 年款。

### 接车页 · 接车结果 · 按图只识一次（2026-10-03）

店员真实顺序：先问清来修什么、核对车型，再连拍进场（仪表与油量经常同一张）。

| 区 | 规则 |
| --- | --- |
| 页序 | **问诊登记** → **品牌车型** → **接车照片**（提示把里程表拍进去）→ **整理** → **接车结果** |
| 取消 | 独立「当前里程」拍摄框；拍前环车勾选；清单里的「仪表（里程）」单独项 |
| 接车结果 | **里程、油量等读数高亮**，店员核对后可改。其余按 **漆面、玻璃、轮胎、灯光、随车物品** 摊图。**不**在接车页输出正常 / 有破损 |
| 识图缓存 | 点「整理」才识图（上传不跑）。识图全文（含未上屏的外观观察）按 **同一张图** 缓存。再点整理、检测整理、发给车主前核对、生成案例：**文件未变则复用，不重跑**。只识新图或换过的图 |
| 检测引用 | **不**自动把接车图变成检测项。检测页：**上传**在上，「**从图库选择**」在下，默认不摊开接车缩略图。钣喷类目提示进场外观已在图库。 |
| 本单图库 | 这本服务相册里传过的图都进图库（不跨单、不跨店）。条目标：拍摄时间、所在步、类目/读数、整理留下的说明。界面不写「大模型 / 自动分析」。检测、工单都可从图库勾进本次照片；按钮写 **选用**，已在本次的写 **已选** |

接车类目 id 见 `INTAKE_RECORD_CATEGORIES`（`odometer` / `fuel` / `paint` / `glass` / `tire` / `light` / `belongings`）。存量 `WALKAROUND_PARTS` 勾选只读兼容，新单不再作为拍前清单。

### 确认前检查（2026-09-14 · 2026-09-26 修订）

店员点「确认并继续」或「通知车主」前，可按**该类服务 × 这一步**给出优化方向。真源见 [`28_`](./28_节点AI检查_用户关心点与开发计划.md)。

| 规则 | 口径 |
| --- | --- |
| **哪些步** | **唯一标准：内容要发给车主看，发出前查一次。** 门店内部「完成」动作一律不触发——施工与完工照车主端不展示（车主时间线只镜像单据节点，见 `buildOwnerFlowView`）；检测随检测报告在送达时一起核对（接车为留证，不参与核对）。**工单**是如实记录施工过程的单据、车主端只读展示，而已确认报价正是它的比对基准，因此**在工单完成时核对一次**（`work_check`，见下条）；完工前不再重复提醒同一问题。因此触发检查的有三条路：**检测报告送达**（报告与方案一次核对，可按报价补检测所见，也可按检测补报价的项目或施工方案，两边都能改）；**报价方案通知车主**（首次，以及车主拒绝后每一次重新提交，与增项同一口径）；**工单完成**（2026-09-28 新增）。车主拒绝退回后门店改完再次提交，清掉上一次结论重新查，不复用旧建议。**是否检查只看「这次是不是发给车主」，不按单据类型挑**，新增单据类型自动纳入；类型只决定用哪套口径（`KIND_TO_STEP` 唯一一份）。车主确认或代确认之后，后续检查不再改已经固定的检测和报价。**完工照、接车与检测不单独跑**；**施工已并入工单**，其检查即工单完成时那一次。工单核的是「工单 × 检测报告 × 已确认报价」三者是否矛盾 / 缺漏，并顺带润色工单文字（口径见 `28`） |
| **向车主确认的环节（都要查）** | 凡是发给车主确认、确认后内容即固定并托管到网站的材料，发出前都过一次检查。判定只看「这次是不是发给车主」，不看单据类型；类型只决定用哪套口径查：检测报告送达（`quote_check`）、报价——**首次以及车主拒绝后的二次、三次、四次……每一次重新提交**（`quote_check`）、施工中新发现的增项（`addon_check`）、完工/交车报告（`delivery`）：车主这次一并看到**施工过程、工单项目、完工照和完工报告**，放进一次里核对——施工过程要与工单项目对得上（对不上改施工侧说明，工单源自已确认报价、不动），完工报告要与施工、工单一致；**接车与检测、报价前期已润色过，这次只作只读参考，不重复润色、不提修改意见**。施工中新发现写在施工节点上不另建检测节点，它通过增项报价向车主确认，同时在完工报告里一并检查 |
| **硬拦 vs 建议** | 缺必填仍硬拦。检查结果贴在**原字段 / 原照片下方**（不同字色与字号）：文案旁「应用」只改这一块；缺图在该部位下补拍，照片并入该项，不另开一项。对不上已有部位才加一行待拍。报价证据、施工图、交车图同样：对得上就加在该项，对不上才新增。发现项默认折叠、一次只展开一项；**有未处理建议的行在折叠态也露出该条**（与补拍条同一位置），展开后再贴到对应输入框下，避免叠两遍。**不**为了展示建议而自动展开某一项。看完后「进入下一步」（通知车主前则「通知车主」）。**不挡下一步，不弹层** |
| **必须先看到再决定** | 建议未出时本步先不完成；等待时主按钮收起，只留一行橙色「正在检查」+ 进行中图标。关掉小程序后打码与分析继续；再打开仍停在本步，建议仍贴在对应位置 |
| **先打码再分析** | 只用打码图问模型；失败不把原图送出去。打码图与建议挂在该节点，托管不再对同图整单重打 |
| **方案怎么才算写好** | 每条报价行的施工方案要写清「做什么工序、用什么件与规格、依据哪条发现」，车主和以后看公开案例的人一眼能看懂。只能用本单已有的检测发现与当前行内容组织句子，**不许编造没拍到、没提到的工序或读数**；不改金额、不做承诺 |
| **不改什么** | 不改金额、不编项目、不建议合并增项轮次；已发给车主的确认件不经店员点不改写 |
| **能力开关** | 总闸关闭或未开通时，本步直接确认，与做本能力之前一致。前期全员免费，以后可按套餐收费（见 `28_` §4.4） |

界面：建议贴在对应内容下，短句、商家口吻。不弹层、不加黄底产品说明。不出现「提示词 / 自动优化 / 大模型 / 套餐」等实现话术。

**施工多图 / 交车选用（2026-09-09）**

- 施工按「维修项」留证：同一部位可多角度。检测同一部位的补拍也并入该项（多图共用检查结果和检查发现）；只有部位对不上时才新开一项。方案证据、交车图同样。  
- **不**再维护与施工平行的第二套「完工相册」；交车图 = 对施工图（及少量补拍）的**引用**，档案不因勾选而复制文件。  
- **整车外观必选**：有施工图也未必含全貌；无外观时仅补拍外观（或从施工图中指定一张为外观），不默认整本重拍。  
- 过程拆解/旧件特写默认不进车主交车区，除非商家勾为交车图或按检查建议补拍。

## 3. 增项（一期）

施工中入口文案：**发现新的待处理项目**（勿写「添加方案」，易歧义）。旁路一句：**下一页拍故障、写看见什么**。点一次即可；已有未发出或待确认的新发现时，再点只回到这一页，不另开一张。  
公网档案**保留**由此产生的多段方案 / 工单 / 施工，不合并、不按主项裁；第二轮方案标题用「施工中新发现」（见 `15_` §7.9）。  

插入一张 **方案确认**（`quote_confirm`，`insertedReason=addon`）。同一页先写 **新发现**（故障照片 + 看见什么），写好后再填 **项目与费用**。项目与费用与首次报价相同：项目、品牌（选填）、施工方案、金额，**不再上传故障图**（照片在新发现里）。车主确认 → **新开工单步**（时间线**另开一张**，与首张工单并列，不合并）→ **继续记录施工**（确认后直达工单步，不必卡在空工单页）→ …  

**单据大标题（商家 + 车主统一）**：**施工中新发现**。时间线段标签可弱标「增项」。  

未发送车主前，方案/增项费用行可 **增删**（至少保留一行空壳便于继续填）。

### 3.1 整张作废（误点入口 / 线下谈妥不做）

- **谁操作**：仅商家。  
- **何时**：增项「施工中新发现」处于未发或等待车主确认；**车主已确认后不可作废**。  
- **未发出（误点）**：直接删掉本张增项及后续未开工单步，**不留时间线记录、不填原因、不通知车主**；当前回到原工单步。  
- **已发送待确认**：作废须 **必填原因**；时间线保留该步，状态「门店已取消」+ 原因（**商家与车主均可见**）；撤掉后续未开工单步；回到原工单步。  
- **车主已确认**：不可作废。  

### 3.2 车主不同意

待确认的方案、施工中新发现、完工确认，车主都可以点 **不同意**。电话联系门店仍保留。

- **施工中新发现**：效果与商家「取消本项」相同（这项不做，回到工单步）。记录为 **车主未同意**，原因记「车主拒绝」，不记成门店取消。车主与门店都看得到。  
- **首次方案、完工确认**：整单不删。单据退回门店可改，状态记 **车主未同意**。门店改完可再发。  

**工单草稿**：打断增项前须落库当前工单草稿；各工单步 `photoDraft.findings` 按 `id` 合并读取，避免项目名丢失。增项后新增的工单项目由商家自行填写，**不预填**。  

**工单合并时机**：时间线保持多张工单（如实按事件发生的顺序记录）；**仅完工确认**汇总全部工单项目与金额（`collectAllWorkOrderItems`，取 `work` 节点 `findings`）。  

二期可加独立「增项检测」拍照节点。

```
工单 ⇄ 施工中新发现 → 工单(增项·独立) → … → 完工照 → 完工确认(合并全部工单项)
```

**验收**：改增项相关代码前后，按 [`27_DOC-FLOW增项最小验收清单.md`](./27_DOC-FLOW增项最小验收清单.md) 点测。

## 4. 单据字段表与生成规则（真源）

> 不用大模型。一期规则生成 + 商家微调。

### 4.1 检测报告 `inspection_report`

| 区块 | 字段 | 规则 |
| --- | --- | --- |
| 页头 | 车辆 / `mileageText` / `chiefComplaint` / `reportDate` | 相册车辆档 + 接车步 `photoDraft.mileageKm`（与仪表照同区；识别可填、以手改为准）；**不要**从发现项图注里猜公里数 |
| 发现项 | `findings[]` | **一项一个对象**：`partName`；`images[]`（该部位的照片，可多张）；`result` ∈ {状态良好, 需关注, 需处理, 仅记录}；`advice`。相册里的照片列表由这项生成。提交时直接校验这项，不按照片地址把结果重新配对 |
| 未检 | `disclaimer` | 落库可保留固定套话；**车主端不展示**该长句，发现项列表上方用分区标题「本次检测项目」 |

> **检测 ≠ 方案。** 检测图回答「查了什么、看见什么」；方案/施工回答「准备做什么」。多张检测图（钣喷多处、故障灯+底盘）可以挂到**同一方案行**。里程表挂在当前里程旁，不进检测发现；液位、环车等选 **仅记录**（或状态良好），**不**生成报价行。  
> **方案不再按发现项一对一预填。** 保养等一项服务会包含多个检测项，所以核对页给空的方案行（或保留商家已写内容），由商家自己写要做的事和金额。照片只留在检测发现项上，一项有几张就显示几张，不挂到方案行。检测结果档**只留在检测报告**，不写进方案/工单行名。  
> **校验**：部位必填；结果必选四档之一；**需关注 / 需处理** 时检查发现必填；**状态良好** 默认「无需处理」（可改）；**仅记录** 不要求检查发现、不进方案证据池。修/换写在**方案处理建议**里。  
> **一项的边界**：照片、部位、检查结果、检查发现属于同一项。补拍只往 `images[]` 里加，不新开一项，也不换掉原照片。相册节点图片是这项的投影；旧数据里只有散图、没有发现项时，才按图注归到同名部位，归不上才新开一项。施工同样是一项多图，只是没有检查结果和检查发现。  
> **分工**：`chiefComplaint` = 客户进店原因；发现项 = 技师所见（含留证图）；方案行 = **准备做什么**与金额。占位按 `templateId`。  
> **废止商家填写「结论」**：一期不以整单结论栏替代发现项。  
> **与已废止「现象/症状」栏的关系**：检查发现写技师所见，不是把客户口述再抄一遍。

**生成**：检测确认 → 报告完整草稿（主诉取接车节点）；方案节点给空行壳，待商家按「要做的事」填写。照片不复制到方案行。  
**门禁（商家）**：在「核对报告与方案」一屏补齐项目名与金额后 **通知车主** → 报告 `delivered` + 方案 `pending_confirm`。  
**车主**：报告可阅、**不确认**；与方案同次出现。

### 4.2 方案确认 `quote_confirm`

| 字段 | 说明 |
| --- | --- |
| `lines[]` | `{ name, brand?, amount, note }`；`name`=**要做的事**（如全车补漆）；`brand`=**配件品牌**（选填）；`note`=施工方案（车主侧称处理建议）；`amount` 为 **真实金额（元）**。首张方案不挂检测图。`evidenceUrl` / `evidenceUrls` 仅增项故障图沿用 |
| `confirmCopy` | **固定协议文案**（商家不可改）：本人同意按上述项目施工，费用以本单为准。 |
| `evidenceRef` | 关联检测报告节点 id（首张方案）；增项以行内证据图为准 |

不按检测部位自动拆行。商家写项目名和金额。存量已按部位拆好的行可继续改、可删并。  
**门禁**：≥1 行且每行 `amount` 为有效数字；**增项**另要求每行有故障图；与报告一并通知 / 增项发送后待确认；车主确认或代确认 → **解锁工单步**（工单项目由商家施工时如实填写，**不再**由报价行派生）。  
**商家编辑**：一行四格——**项目**（要做的事，如更换机油机滤）/ **品牌**（选填）/ **施工方案**（怎么做，如机油标号和更换范围，不要把项目名再写一遍）/ **金额**。不放检测图。**不展示**确认文案；车主确认页仍称处理建议。

### 4.3 工单 `work`

工单是**如实记录施工过程产生的单据**，不是报价的复刻。商家在施工过程中逐条记录实际做了什么。

| 字段 | 说明 |
| --- | --- |
| `findings[]` | 工单项目，逐条如实记录。一项 = `{ id, partName, caption, material?, brand?, qty?, amount?, images[] }` |
| `partName` | 项目 / 部位名（商家自由填写） |
| `caption` | 施工说明：做了什么、结果如何 |
| `material` | 用料（实际换上的件） |
| `brand` | 品牌（选填，便于与报价约定的品牌核对） |
| `qty` | 数量（选填） |
| `amount` | 金额（**选填**）。填了则必须与已确认报价一致；不一致须走增项确认后才能发出（见 §4.4） |
| `images[]` | 施工过程图，挂在**本项**上（一项可多图） |

**填写**：商家自由填写，**不要求**与检测发现项或报价行一一对应——两者文案本就不必相关。

**门禁**：≥1 项且每项有 `partName`；每项至少 1 张图。

**工单完成时核对**（`work_check`，见 `28`）：模型拿本段工单与检测报告、已确认报价比对，提示矛盾与缺漏，并润色文字。**只在工单完成时核一次**，完工前不再重复提醒。

**多工单并存**：每次增项开一张新工单，在时间线**并列、不合并**，如实按事件发生的顺序记录；仅**完工确认**汇总全部工单项目。

**车主侧**：单据时间线里只读展示（施工项 + 用料 + 图），**不需车主确认**。

### 4.4 完工确认 `repair_report`

| 区块 | 字段 |
| --- | --- |
| 已施工 | 全部工单 `findings`（含增项工单），由 `collectAllWorkOrderItems` 汇总 |
| 合计 | **以工单为准**：工单项目填了金额 → 取工单合计，且**必须与已确认报价一致**（不一致须先走增项确认，否则阻断发出）；工单未填金额 → 回落到已确认报价（含增项）合计 |
| 验证 | `deliveryPhotos[]` |
| 质保 | **期限**（必填、实质内容）+ **注意事项**（选填；范围/除外等合写）；存量 scope/exclusions 读侧拼入注意事项 |
| 确认文案 | **固定协议文案**（商家不可改） |

**生成**：完工照确认后。车主确认或代确认成功后，**自动整单完工**（相册 `completed`）。

## 5. 确认与代确认

**需车主确认**：仅 `quote_confirm`（首张「方案确认」/ 增项「施工中新发现」）、`repair_report`（完工确认）。  

**不需**：`inspection_report`（随方案通知后可阅）、`work`（工单，只读展示）。

**确认文案**：平台固定协议句，写入单据 payload；**商家报价/完工编辑页不展示、不可改**；**车主确认页展示**。

### 商家操作两阶段（方案 / 增项 / 完工）

| 阶段 | 单据状态 | 商家底栏 | 状态文案 |
| --- | --- | --- | --- |
| 编辑 | `draft` | **仅**主按钮「发送车主确认」（发送时保存；**不**单独「保存草稿」） | **不标「草稿」**（摘要可空） |
| 待确认 | `pending_confirm` | 提示「等待车主确认」+ 次按钮「代车主确认」 | 待车主确认 |

**商家代确认**：仅在「待确认」阶段出现，入口为次按钮「代车主确认」。点后先弹窗确认前提——**仅限车主当面、电话或微信已同意，但未在手机确认**；确认后再二选一：**附同意截图（聊天记录即可）** / **不留痕，直接确认**（在确认流程内选传，**不**单独占一行「上传证明」按钮）。

| 状态 | 展示 |
| --- | --- |
| draft | （商家面不展示「草稿」标签） |
| delivered | 已送达（检测报告，随「通知车主」写入） |
| pending_confirm | 待车主确认 |
| confirmed | 车主已确认 / 商家代确认 + 时间；代确认可选证明图 |

### 6.3 发现项 `finding`（一项的边界）

**属于同一发现项的字段必须住在同一个对象里。禁止按数组下标或图片 URL 跨数组配对。**

| `partName` | string | 部位 / 施工项目名。**不是身份**，可重名、可改 |

### 6.4 `id` 规则（真源）

1. **新建** finding 必须分配 `id`。
2. **读取**：`normalize*` 保留 `raw.id`；缺失时按下述顺序生成，且生成后**立即持久化**（页面有自动保存，存量数据打开一次即完成迁移）。
   - 首图指纹：`fid_<媒体键>` —— 同一张图多次 normalize 得到同一 id
   - 仍取不到：`fid_i<下标>` —— **仅存量首次迁移命中**
3. `id` 落库后不随顺序调整、改名、换图而变化。删除项后其 `id` 不复用。

### 6.5 配对规则

- **一律按 `id` 配对**。禁止用数组下标、展示顺序、图片 URL 反查，把 `photos[]` 与 `findings[]` 对齐成一条记录。多图挂在 finding 的 `images[]` 上。
- **禁止用 `partName` 当主键**做合并或匹配（部位可重名）。同名不同 `id` 视为两项。
- 工单项目与检测发现项 / 报价行**不建立对应关系**（2026-09-28 起，两者文案不必相关）。存量数据里的 `quoteLineId` **只读保留；读侧不再用于配对，新写入不再产出**。
- 散图与 finding 的关联只认 `imageId` / `url`。位置兜底仅允许在存量「一图一项」且两侧数量相等时启用一次，生成 `id` 后不再命中。

**存量兼容**：旧形状在 normalize 里只读不写回；新写入必须是本节结构。

### 6.6 工单项目如实填写（废止预生成）

> **2026-09-28**：废止「按报价行 / 工单 `items` 预生成施工项骨架」。工单项目由商家**如实填写**，与检测发现项、报价行**不建立勾连**。

1. 进入工单步时项目**不预填**：商家按实际施工逐条新增，一项 = `{ id, partName, caption, material?, brand?, qty?, amount?, images[] }`（字段表见 §4.3）。
2. 项目名（`partName`）**由商家填写**，**不再**从报价行带入；检测结果档只留在检测报告，不写进工单行名。
3. 图挂在**本项**的 `images[]` 上（一项多图），**不**按图 URL 或数组下标与别处对齐。
4. **不要求** `quoteLineId` 勾连；存量数据里的 `quoteLineId` **只读保留，新写入不再产出**（见 §6.5）。
5. 展示顺序 = 商家填写顺序，新增项排在末尾。

**多工单并存**：增项工单与首张工单在时间线**并列、不合并**（§3、§4.3），如实按事件发生的顺序记录；仅**完工确认**汇总全部工单项目（`collectAllWorkOrderItems`，取 `work` 节点的 `findings`）。

**增项流程**（施工中新增项目）——不在施工节点自由添加，回到方案侧闭环：

1. 商家点「发现新的待处理项目」→ 插入 `quote_confirm`（`insertedReason=addon`）
2. 车主确认或商家代确认
3. 自动**新生成一张增项工单**（与首张工单**并列、不合并**），并插入一个新的施工步（带入前序已传 findings）
4. 新施工步**不预填**工单项目：商家按实际施工逐条新增（与首张工单同一口径，见 §6.6）；前序已传的图保留不丢，**不再**按 `quoteLineId` / 名称归位

## 7. 门禁

- 过程步必填硬拦截（主诉/发现项/质保）。  
- 「通知车主」：报告完整 + 方案金额硬校验。  
- 整单完工：完工确认（车主确认或商家代确认）成功后**自动**将相册标为 `completed`（通知、预脱敏等）；不再要求商家二次点「标记整单完工」。存量若步骤已齐但相册未完工，商家端可保留一次补点入口。
- **案例托管**：相册 `completed` 后，flow 页底栏出现「托管到案例站」；编辑页只读态同入口。主路径为**原始档案托管**（私密 / 公开二选一），废止「本地生成优化案例稿再推送」。公开须隐私校验 → **内容检查（软建议）** → 生成 GEO → 门店确认 GEO 后才上店页（见 `15_` §7.11 · `19_`）。缺里程不拦完工，公开前警告。
