# 施工节点即验收 + 交车节点只做交付确认

## 1. 背景与已确认决策

- **验收前移到施工节点**：施工项的「施工说明」写清做了什么、怎么做、结果如何，并配施工图片，即视为该项验收通过。不再单设验收环节。
- 交车节点**不再展示任何逐项验收内容**（不显示验收清单、验收结果、验收图、验收 AI 建议）。
- 交车节点只保留：交车外观照（选填）、质保期限/说明、交付人、交车时间、交付里程，以及「发现问题」三出口。
- 施工 AI 改为按**一般性验收标准**判断每个施工项是否已施工完成，并给出施工说明的润色/修改建议；不再以「补拍清单」为主线。
- 交车 AI 不再做验收判定，只产出质保建议、提醒、简述、问答、图说等交付文案。
- 施工节点完成后锁定；允许追加新事实，不允许篡改旧记录。
- 交车时发现新问题三出口：本单追加 / 转新单 / 返工。
- 已确认：
  1. 交付里程必填，默认带检测里程、可改。
  2. 报告已发送后允许追加并生成修订版 v2，旧版保留。
  3. 施工完成硬性要求每个施工项至少 1 张图。
  4. 外观照选填，无图需确认豁免并留痕。

## 2. 流程

```
检测 → 报价 → 施工（施工说明 + 图片 = 验收通过；未施工项交代）
     → 交付确认（外观照 / 质保 / 交付信息）
     → 自动生成报告 → 发车主确认 → 交付完成
```

交车时发现新问题：

- A 当场追加（默认）：插入补充报价 → 施工回 `in_progress` → 追加施工 → 重新生成报告版本。
- B 转新单：新建相册（继承车辆/客户/门店）→ 双向关联 → 原单报告写「建议观察」。
- C 返工：选择项目 + 原因 → 施工回 `in_progress`，不计费 → 报告标注返工。

分流：同一故障链、当场能修 → A；需订件/跨天/另一件事 → B；之前施工有问题 → C。

状态：

- 施工：`in_progress` ↔ `locked`（A/C 可回退）。
- 交付确认：`pending` → `completed`（A/C 回退）。
- 报告：`draft` → `pending_confirm` → `confirmed/delivered`；已发后修改 → `revision+1` 重新发送。

## 3. 前端交互规则

### 3.1 施工节点（唯一留证 + 验收节点）

1. 每个施工项包含：项目名、施工图片（1–6 张）、施工说明。
2. 施工说明字段标签为「施工说明」，提示语引导写清：做了什么、怎么做的（用料/工序/关键参数）、结果如何。
3. 文案明示：施工说明 + 图片提交后即视为该项验收通过，交车不再重复验收。
4. 完成校验：
   - 未施工报价项必须交代（保留）。
   - 每个施工项至少 1 张图。
5. 完成后照片与说明锁定，交车不再补拍；疑似返工可标记并写入 `reworkRecords`。
6. AI 建议卡片：显示「已完成 / 待确认」判定、判定依据、施工说明建议或润色建议；说明为空时给「应用」，已有说明时给「润色」（替换原文）。

### 3.2 交付确认页

1. **不再渲染逐项验收清单**（项目名、施工图、验收结果、AI 验收建议全部移除）。
2. 交车外观照：0–4 张选填；无图完成需确认，记录 `exteriorPhotoWaived`。
3. 交付信息：质保期限（必填，AI 可应用）、质保说明（选填）、交付人（默认当前店员，必填）、交车时间（默认当前，必填）、交付里程（默认检测里程，必填）。
4. 按钮：「生成交车报告」为主；「发现问题？」为次入口。
5. AI 建议面板只保留：质保期限建议、交付提醒；不再有验收建议、图片挪行建议。

### 3.3 报告页

1. 进入自动生成，无需输入。
2. 内容：施工项目清单（含施工说明 + 图片）、简述、快速问答、质保、交付信息、交付里程、返工/遗留项。
3. 不再生成验收清单章节；历史报告已存内容不回溯。
4. 未发送可重新生成覆盖草稿。
5. 已发送显示版本号；追加/返工后生成 v2，旧版可追溯，并提示车主查看修订版。
6. 发送后 `pending_confirm`，车主确认即完成。

### 3.4 「发现问题」弹层

| 操作 | 必填 | 结果 | 限制 |
|---|---|---|---|
| 当场追加 | 说明 ≤200 字，可选 6 张新问题图 | `insertAddonPlan`，跳补充报价 | 已发报告提示将出 v2 |
| 转新单 | 说明 | 新建相册并双向关联 | 已交付后仍可用 |
| 返工 | 说明 + 选择项目 | 施工回 `in_progress`，交付暂停 | 记录操作人 |

只读/已交付状态下禁用并解释原因。

## 5. 施工节点 AI 提示词改造

### 5.1 定位

- 施工节点是唯一留证与验收节点：说明 + 图片就是验收证据。
- AI 按一般维修验收标准判断「这一项是否已经施工完成」，而不是只检查照片够不够。
- 图片只在无法判断完成时提示缺什么，不作为主输出。

### 5.2 一般验收标准（写进提示词）

| 项目类型 | 判定要点 |
|---|---|
| 更换件（胶套/刹车片/电瓶/轮胎等） | 旧件已拆下、新件已装配到位、紧固/扭矩已复紧、试车或功能检查无异常 |
| 油液类（机油/变速箱油/冷媒等） | 液位符合要求、无渗漏、规格/用量匹配 |
| 钣喷类 | 底材处理到位、色差可接受、平整度/缝隙正常、无流挂 |
| 检查/清洁类 | 检查结论明确、处理动作已执行、结果可复核 |
| 改装/加装类 | 安装牢固、线路/管路规范、功能可用、不影响原车功能 |

判定输出仅两档：

- `已完成`：说明或图片能支持上述要点，无明显缺失。
- `待确认`：说明缺关键动作/结果，或图片无法证明完成；在「缺少」写明缺什么。

### 5.3 输出规则（`workInstruction`）

| 规则 | 要求 |
|---|---|
| 逐项完成判定 | `证据:[{项目, 判定:"已完成"|"待确认", 依据, 缺少}]`；项目名必须取自工单项目或报价项 |
| 说明建议 | 说明为空：给「建议描述」，按“做了什么 + 怎么做的 + 结果”成句 |
| 说明润色 | 说明已写：给「修改建议」，输出**完整替换句**，保留原意、补关键工序与结果，不凭空加事实 |
| 缺图提示 | 只有图片无法判断完成时才写「缺少」；不输出大段补拍清单，不要求交车补拍 |
| 未施工项 | 已交代不再提醒；报价有、施工无且未交代，标「报价有、施工无」 |
| 疑似返工 | 给「返工提醒」+ 画面依据，不擅自改状态 |
| 禁止甩锅 | 不出现「交车时补拍 / 交车再确认」 |

### 5.4 数据结构与兼容

- JSON 键保持 `证据` / `填写建议` / `逐图归类` / `拆分建议` / `返工提醒` / `新增项`，减少前端改动。
- `证据` 解析为 `evidence: 'done' | 'pending'`，并写入 `completionBasis`；老数据 `sufficient → done`、`insufficient → pending`。
- `填写建议` 增加 `修改建议`：解析为 `polish`；前端 `canPolish` 时按钮为「润色」，点击**替换**施工说明。
- `补拍清单` 不再由新提示词产出；解析器保留以兼容老 AI 结果。
- 指纹 `work_v9`（交车 `delivery_v8`），上线后老单自动重出建议。
- 技术文件：`backend/src/services/step-advice.service.js`（`workInstruction`、`parseWorkAdvice`、`contextOf`、`fingerprintFor`）。

### 5.5 交车 AI 减法

- 删除提示词里的「验收」与「拆分建议」，只保留：质保期限、提醒、简述、问答、图说。
- `parseDeliveryAdvice` 不再解析 `验收` / `拆分建议`；`acceptance` / `groups` 返回空。
- `adviceHasContent('delivery')` 不再以 acceptance 为判空依据。
- 前端 `deliveryAdvicePanel` 删除「验收建议」「图片挪行建议」两块；`decorateDeliveryAdvice` 只保留 warranty/tips。
- `onApplyDeliveryAdvice` 只保留 warranty 分支；acceptance/split 分支删除。

## 7. 验收用例

1. 施工项缺图无法完成；未施工未交代无法完成。
2. 施工说明填「做了什么/怎么做/结果」并配图后，完成施工节点即视为验收通过。
3. 交车页看不到逐项验收清单与验收 AI 建议，只看到外观照与交付字段。
4. 交车无外观图可完成（需确认豁免），质保/交付信息齐全即可。
5. 施工 AI：说明为空给「建议描述」可应用；已有说明给「润色」可替换；判定显示「已完成 / 待确认」。
6. 交车 AI 不再返回验收建议，只返回质保/提醒/简述/问答/图说。
7. 报告不再出现「验收」章节，施工项目清单含说明与图片。
8. 交车页追加 → 施工回 `in_progress`、补充报价插入、报告回草稿。
9. 已发报告追加 → v2，v1 可查。
10. 转新单 → 双向关联；返工 → 施工重开、报告标注返工、不计费。
